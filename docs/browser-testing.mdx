## Start and observe a development server

Configure **Settings → Repos → Dev Server Script**, or use **Edit dev server script** in the Workspace **Logs** view. The existing managed server controls start and stop the Workspace's scripts, show process state, and let you select each repository's logs. The context bar's Dev Server action (`T D`) opens Logs when starting. Running describes the managed process; check the logs and application separately for readiness.

The same manager serves UI, stdio MCP and remote MCP start/stop/status operations. Starting an already running server reuses it. A failed script or uncertain process cleanup is not proof that the application is ready or stopped.

## Open the application

In **Logs**, select the development server and copy its detected URL or choose **Open in browser**. You can enter a reachable application URL in that field; it is a temporary override for the selected process. Only HTTP and HTTPS URLs without embedded credentials are accepted. Changing the selection resets the override. Detection does not establish network reachability or application health.

A URL printed by a server belongs to that server's network environment. On the same machine, open its localhost URL directly. In WSL or a container, check the configured port forwarding. On a VPS, `localhost` in your laptop's browser refers to your laptop, not the VPS. Use an existing permitted public route, VPN, or an SSH tunnel for a private application. LVK does not create tunnels or publish applications automatically.

For example, if the application listens on port 5173 of the SSH host:

```bash
ssh -N -L 15173:127.0.0.1:5173 your-user@your-server
```

Keep that SSH session open and visit `http://127.0.0.1:15173` in your browser. If the application runs inside a container, the SSH host must already have a permitted path to its application port; host loopback does not mean container loopback. Configure the application's allowed hosts and WebSocket/HMR public URL for the chosen path. A tunnel does not make a URL reachable by an external AI.

For public HTTPS routes see [Independent application routes](/self-hosting/server-container#independent-application-routes). DNS, TLS, application authentication and public HMR settings remain the application's operator's responsibility. These routes do not inherit an LVK login or its Basic authentication.

## Inspect and test

Use your browser's DevTools for responsive layouts, console, network and DOM inspection. Implementation agents can continue to use the distribution's Chromium, Playwright and CDP/MCP environment. External AI tools need an application URL and authentication they can actually access.

LVK no longer embeds an iframe browser, injects Eruda or component inspection scripts, or sends clicked components into chat. This intentionally removes click-to-component, integrated viewport controls and embedded navigation. Existing component context in saved chats and historical preview Scratch settings remain readable; they do not reactivate the feature. Workspace file, Markdown, diff and image previews remain available.

## Retired settings

`LVK_PREVIEW_DOMAIN`, `VK_PREVIEW_DOMAIN`, `PREVIEW_PROXY_PORT` and `VK_PREVIEW_DISABLE_NAV_SCRIPT` no longer enable a browser or proxy listener. Remove them from old environments. Retained values are ignored with a retirement warning and do not by themselves prevent startup. The old wildcard URL, preview authorisation handoff/cookie and `/api/preview/...` proxy API are retired. Existing SQL migrations and LVK login sessions are retained.

`LVK_PREVIEW_ROUTES` remains supported and is independent. LVK does not automatically convert an authenticated old wildcard route into an unauthenticated application route. Choose a private tunnel or provide the application's own authentication before exposing it. Vite's built-asset `preview` command is unrelated to the removed embedded browser.
