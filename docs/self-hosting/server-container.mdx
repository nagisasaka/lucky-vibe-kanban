---
title: "LVK self-hosted server"
description: "Run LVK on a public IP with automatic HTTPS, locked setup, Basic or Auth0 authentication and persistent Docker volumes. No domain required."
---

Run LVK and its agents on an always-on server, then use LVK in your laptop's browser. Closing the browser or putting the laptop to sleep does not stop a server-side run. Stopping the container, rebooting the server or losing power does stop its processes; persistent volumes preserve data, not executing processes.

This distribution runs the **local LVK application** remotely. It does not require PostgreSQL, ElectricSQL, upstream billing access or a relay service.

<Warning>
  This is one trusted team's development environment, not an isolated multi-tenant
  service. The Basic owner or approved Auth0 members can operate agents and access
  all repositories. Agents share the same Linux user as LVK and
  nginx. Read-only secret mounts prevent overwriting, not reading. Use a
  dedicated server, restrict ingress to your IP/VPN where possible, and do not
  mount the Docker socket, your host home or cloud administrator credentials.
</Warning>

## What the image contains

- Prebuilt LVK frontend, Rust server, sibling `agent-process-host` executable and `vibe-kanban-mcp` CLI.
- nginx with HTTPS on host port **443**, backed by LVK authentication. The optional certificate companion uses port **80** only for certificate validation.
- Codex CLI, OpenWiki, Node.js, pnpm, Git, Git LFS, GitHub CLI and Python.
- The repository's pinned Rust toolchain, rustfmt, Clippy, cargo-watch, C/C++ compiler, CMake and native build dependencies for developing LVK itself.
- A non-root runtime user, `appuser` (**UID/GID 10001**).

The serving binaries live in `/usr/local/bin`, not in a project's checkout. Editing or building LVK in `/repos` does not replace the application that is managing that work. Additional agent CLIs and project-specific SDKs can be added with a derived image.

The initial published platform is **Linux amd64** (x86-64 EC2, not Graviton/ARM). Resource needs depend mostly on your builds and concurrent agents. The image is deliberately larger than a minimal runtime image because it contains a development toolchain.

## Prepare the host

You need Docker Engine, Docker Compose v2, a stable **public IPv4 or IPv6 address**, and disk space for images, repositories and build caches. You do not need to buy a domain or configure DNS. Private/LAN addresses cannot receive public Let's Encrypt certificates.

Allow inbound TCP **80 and 443** in the cloud and host firewalls. Port 80 must remain reachable by Let's Encrypt for future validation; it serves challenge responses only, never the application. Do not expose raw application ports 3000, 3001 or project development ports. The optional source development environment below publishes its own authenticated HTTPS endpoint on port 8443.

Copy `compose.yaml`, `compose.acme.yaml`, `acme.py`, `.env.example` and `.gitignore` from `deploy/server` at the **same source tag as the image** into a dedicated directory on the host. You do not need to clone or compile LVK.

Copy `.env.example` to `.env`. Set your published image reference and replace the documentation IP below with your server's public address:

```dotenv .env
# Replace VERSION with an actually published version, or use an immutable digest.
LVK_IMAGE=ghcr.io/nagisasaka/lucky-vibe-kanban:VERSION
LVK_HOST=203.0.113.10
COMPOSE_FILE=compose.yaml:compose.acme.yaml
LVK_ACME_AGREE_TOS=yes
LVK_ACME_EMAIL=
LVK_PREVIEW_DOMAIN=
```

Read the [Let's Encrypt subscriber agreement](https://letsencrypt.org/repository/) before setting `LVK_ACME_AGREE_TOS=yes`. The contact email is optional. Keep the Compose project name (`lvk-server`) stable: changing it selects different named volumes. For IPv6, set `LVK_HOST` without brackets and use brackets in the browser URL, for example `https://[2001:db8::10]`.

## Prepare authentication

New public deployments start locked and expose no business data before setup.
Follow [LVK authentication and Auth0 setup](/self-hosting/authentication) to issue a
one-use setup key and configure Basic or Auth0 in the browser. There are no default
credentials. Existing `secrets/htpasswd` files retain their nginx protection until
you explicitly migrate; the authentication guide gives the transition steps.

Prepare the certificate directory before starting Compose:

```bash
mkdir -p secrets/tls
docker compose pull
sudo chown -R 10001:10001 secrets
sudo chmod 750 secrets secrets/tls
```

The certificate companion obtains a trusted certificate before Compose starts LVK. IP certificates last approximately six days; the companion checks hourly and lets Certbot decide when renewal is due. Failed attempts are retried after 15 minutes. The ACME account and renewal configuration stay in a separate `acme` volume, inaccessible to agents.

The companion exports matching certificate/key pairs through an atomic directory link inside `secrets/tls`. LVK reads this directory as read-only, validates each changed pair and reloads nginx within 30 seconds. The backend and its agents keep running. Certificate files use UID/GID 10001 and mode 640. LVK refuses to start with an expired certificate, a certificate for another address, or a mismatched key. Explicit legacy-proxy mode also requires a valid bcrypt password file.

## Use a domain or your own certificate issuer

For an optional domain, set `LVK_HOST=lvk.example.com` and point its DNS at the server. The automatic companion supports a single app hostname as well as an IP address.

Public project preview origins are currently denied by the Auth0 access boundary; local preview is retained. See the authentication guide for this limitation.

If you already manage TLS, set `COMPOSE_FILE=compose.yaml` to omit the certificate companion. Provide these files yourself; symlinks must resolve within the mounted `secrets` directory:

```text
secrets/
├── htpasswd
└── tls/
    ├── fullchain.pem
    └── privkey.pem
```

Set certificate ownership to UID/GID 10001, directory modes to 750 and file modes to 640. The certificate must cover the app IP/DNS name and, when enabled, `*.LVK_PREVIEW_DOMAIN`. Wildcard certificates usually require DNS-01 validation. The automatic companion intentionally rejects a non-empty `LVK_PREVIEW_DOMAIN`; it cannot obtain wildcard certificates using its IP/HTTP validation flow. In this externally managed mode only port 443 is published.

## Start and sign in

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 lvk
```

Open `https://YOUR_PUBLIC_IP` (or your optional hostname), obtain the setup key with `docker compose exec lvk server setup-token`, and complete [authentication setup](/self-hosting/authentication). Before setup, the login assets are public and business APIs/streams are locked. Existing nginx Basic credentials remain required during migration. Health checks verify the internal health route and the public TLS certificate. A failed service causes the supervisor to stop its sibling; `restart: unless-stopped` restarts the container. An `unhealthy` status alone does not cause Docker to restart it.

Authenticate Codex once, from a terminal on the host:

```bash
docker compose exec lvk codex login --device-auth
docker compose exec lvk codex login status
```

Open the printed link in your laptop's browser and enter the one-time code. Device-code login may need to be enabled in your ChatGPT account/workspace. This avoids exposing a localhost OAuth callback port. See [OpenAI's headless authentication instructions](https://learn.chatgpt.com/docs/auth#login-on-headless-devices) for account requirements and alternatives. Codex credentials and sessions live under the persistent user home; treat that volume and its backups as secrets.

Configure Git identity as `appuser`, clone your project into `/repos`, and select that server-side path in LVK:

```bash
docker compose exec lvk git config --global user.name "Your Name"
docker compose exec lvk git config --global user.email "you@example.com"
docker compose exec lvk git clone https://github.com/nagisasaka/lucky-vibe-kanban.git /repos/lucky-vibe-kanban
```

For private repositories, authenticate the bundled GitHub CLI or configure a repository-scoped deploy key inside the persistent home. Do not bake credentials into a derived image. A server-side folder picker cannot open your laptop's native file dialog; use the server path input instead. Configure SSH editor integration when opening server workspaces from your desktop.

For LVK's MCP integration inside the container, you can configure the bundled `vibe-kanban-mcp --mode global` command instead of an npm download. It connects to the local backend. The image does not overwrite your agent's MCP configuration.

Agent approval and sandbox settings remain under LVK/Codex control. Container hosts differ in their support for nested sandbox mechanisms. If a run reports a sandbox/namespace error, investigate the specific restriction; do not make the container privileged, mount the Docker socket or disable agent safeguards as a blanket workaround.

## Develop LVK on the server

Use the contributor workflow in `deploy/developer/STAGING.md`. Keep the stable
image running on HTTPS 443. Build and run a separate instance from each card's
worktree, with its own `LVK_INSTANCE_DIR` and internal port, then run headless E2E
against that instance. No additional development container or source watcher is
required.

For human verification, add `deploy/developer/compose.staging.yaml` to the host's
Compose files. It exposes HTTPS 8443 through the same container to an explicitly
started staging process on internal port 4020. Build the integrated main revision
with `pnpm run staging:build main`, then start the printed build ID with
`pnpm run staging:run BUILD_UUID`.

Staging has its own database and authentication setup. Run the staging build's
`server setup-token` with the same `LVK_INSTANCE_DIR` as that process, and enter
the key at the staging HTTPS URL. A stable setup key does not configure staging.
Stop staging and other instance/build processes before requesting a stable image
update. Publishing an image does not deploy it.

The old `compose.development.yaml` and `--legacy-development` updater option are
retained for existing installations only. Do not use them for a new contributor
installation. Agent credentials stay in the persistent home; application data
and execution state are isolated by the instance directory.

## Project previews

The domain-free setup runs the application and agents, but does not provide wildcard browser previews. You can use SSH port forwarding to reach project development servers, or opt into the separate preview domain with externally managed TLS. Project HTML must remain on a separate origin from LVK.

With previews enabled, a development server on port 5173 is reached as `https://5173.preview.example.com`, not your laptop's `localhost`. LVK exposes this domain through its system-info API and uses it in the preview pane. HTTP redirects, Next.js redirect headers, streaming and WebSocket/HMR requests use the proxy.

- Start development servers inside the LVK container; loopback listeners are sufficient.
- Use unprivileged ports 1024–65535 except **3000, 3001 and 8443**, which are reserved for LVK/nginx.
- With backend authentication, authorise each preview origin from an authenticated LVK session. Preview cookies are separate from the LVK session and cannot access its APIs. Open previews in a separate tab when third-party cookies are blocked. Legacy proxy Basic can remain as an additional restriction.
- LVK session cookies and credentials are removed before forwarding to a project server. The managed application ingress forwards Web credentials to LVK, which performs authentication.
- Project-controlled HTML is never served through `/api/preview` on the main LVK origin. The public proxy is single-host; remote relay previews are not supported by this distribution.
- External assets or absolute `localhost` URLs hard-coded in a project's HTML/JavaScript are not automatically rewritten. Configure that application's public URL/HMR options where needed.

## Persistent storage and build caches

| Volume  | Container path  | Contents                                                                              |
| ------- | --------------- | ------------------------------------------------------------------------------------- |
| `home`  | `/home/appuser` | LVK database/configuration, credentials, agent sessions, Git settings, package caches |
| `repos` | `/repos`        | Original Git repositories and their untracked files                                   |
| `work`  | `/var/tmp`      | LVK worktrees, shared resources and run-related temporary storage                     |

Release data includes `/home/appuser/.local/share/vibe-kanban/db.v2.sqlite`. Release worktrees/shared resources are under `/var/tmp/vibe-kanban`; a development checkout uses `/var/tmp/vibe-kanban-dev`. Both are covered by the `work` volume. Keep custom worktree roots inside these mounts, or explicitly add another persistent mount.

LVK's `.lvk-shared/persistent` and `.lvk-shared/cache` links continue to work across cards. Cargo does not automatically use the shared cache: configure the project's target directory when appropriate. Do not share one `cargo clean` operation across concurrently active worktrees. The kit does not modify project settings or inject language-specific cache policies.

Do not use `docker compose down -v`, `docker volume prune`, or host temporary-file cleanup against these volumes: those operations can delete the database, credentials or worktrees. Restarting/recreating the container with the same named volumes preserves data.

## Renew certificates and rotate credentials

With `compose.acme.yaml`, renewal and nginx reload are automatic. Keep the certificate service running and port 80 reachable. Inspect `docker compose logs certificates` for validation failures; both the certificate service and LVK become unhealthy when their certificate has less than six hours remaining. Docker health status is not an alerting service: monitor it and the externally served certificate with your normal monitoring tools.

To test the validation path against Let's Encrypt staging without replacing the live certificate, stop the hourly checker temporarily to avoid competing Certbot processes, then run:

```bash
docker compose stop certificates
docker compose run --rm --no-deps --service-ports --entrypoint certbot \
  certificates renew --cert-name lvk --dry-run --no-random-sleep-on-renew
docker compose start certificates
```

Restart the certificate service even if the dry run fails. Do not use `--force-renewal` for routine checks: it needlessly consumes issuance limits. Keep the `acme` volume across upgrades and reboots. If the public IP changes, update `LVK_HOST` and recreate the services; existing browser bookmarks and certificates do not follow a changed IP.

With externally managed TLS, your issuer's deployment hook must replace the matching full chain and private key inside `secrets/tls` with UID/GID 10001 and mode 640. LVK detects the change, validates it and reloads nginx automatically. It logs and retries invalid or incomplete replacements while the previous nginx workers continue serving.

Manage backend Basic/Auth0 credentials, members and recovery through [authentication setup](/self-hosting/authentication). LVK Web sessions support logout and revocation. If you retain legacy nginx Basic as an additional restriction, updating `htpasswd` affects subsequent proxy checks; it does not replace LVK session management.

## Back up, update and roll back

Pause or finish agents before maintenance. Stop LVK before copying its SQLite database so that the database, journals, Git worktrees and their metadata form one consistent backup. Back up **all three volumes together**, plus the deployment `.env`, secrets and `acme` volume, using your encrypted backup system.

For a manual backup from the deployment directory:

```bash
umask 077
docker compose stop
backup_dir="backups/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$backup_dir"
docker compose run --rm --no-deps -T --entrypoint tar lvk -C /home/appuser -czf - . > "$backup_dir/home.tar.gz"
docker compose run --rm --no-deps -T --entrypoint tar lvk -C /repos -czf - . > "$backup_dir/repos.tar.gz"
docker compose run --rm --no-deps -T --entrypoint tar lvk -C /var/tmp -czf - . > "$backup_dir/work.tar.gz"
# Back up .env and secrets with your encrypted secret-backup procedure as well.
```

Check each command's exit status and verify the archives before upgrading. Some host policies remove old files in `/var/tmp`; Docker's named-volume data must be exempt from such cleanup. Volume contents may include sensitive prompts, source code and tokens.

After a successful backup, select the new version/digest in `.env`, then:

```bash
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100 lvk
```

Verify that existing cards, conversation history, repositories and shared files remain, then run a small agent task. A container restart does not promise automatic resumption of an interrupted Goal; inspect its state and resume intentionally through LVK.

For rollback, stop the new container and restore the matching backup of **all three volumes** into a separate recovery deployment with the same internal paths, select the old image digest, and validate it before switching traffic. Do not simply run an older image against a database that a newer version has migrated. Keep the original deployment and backups until recovery is verified.

## Extend the development environment

### Run browser E2E inside the server

The standard server image includes headless Chromium, its system libraries and
a pinned Playwright runtime. You do not need a desktop or a browser on your
local computer. The browser binaries live at `/opt/lvk-browsers`, outside the
persistent home volume, and Compose provides 256 MB of shared memory.

From the LVK checkout inside the stable container, run the real application
checks against your development URL:

```bash
export LVK_E2E_BASE_URL=https://YOUR_SERVER:8443
export LVK_E2E_CREDENTIALS_FILE=/path/to/protected-credentials.json
pnpm run server:e2e
```

The credential file contains the JSON keys `username` and `password` for HTTPS
Basic authentication. Keep it outside Git. TLS verification remains enabled.
The checks render and reload the application, call its real backend and check
that anonymous HTTPS access fails. They do not create agent runs or modify cards.
Use the separate development database for feature tests that change data.

`pnpm run workflow:e2e` continues to run the UI fixture suite at port 4175.
The two suites serve different purposes. Use the repository's pinned Playwright
version to match the bundled browser. Other projects can set
`PLAYWRIGHT_BROWSERS_PATH=$HOME/.cache/ms-playwright` and run their own
`pnpm exec playwright install chromium` without root.

### Optional updater for LVK contributors

The repository's `deploy/developer/README.md` describes the optional Linux host
service for developing LVK using LVK itself. Install it separately on the host;
it is not part of the standard application image and does not expose Docker to
application agents. It accepts an explicit update request, validates the fork's
successful release and image digest, waits for idle applications, backs up their
persistent data, applies the image and verifies browser/backend operation.

The kit supplies the development E2E URL and credentials through an optional
Compose overlay. Its HTTPS maintenance gate returns 503 during replacement.
An active agent must end its run after submitting an update so that the host can
proceed. Interrupted host transactions remain recorded for recovery via SSH.
Source editing and the development server's reload loop do not build images.

### Add another SDK

Build a derived image in your own CI when you need another SDK or coding agent. For example:

```dockerfile Dockerfile.custom
FROM ghcr.io/nagisasaka/lucky-vibe-kanban:1.2.0
USER root
RUN apt-get update \
 && apt-get install -y --no-install-recommends jq \
 && rm -rf /var/lib/apt/lists/*
USER appuser
```

Replace the example base with your published version/digest. Preserve the non-root user, entrypoint, internal ports and storage paths. Point `LVK_IMAGE` at your derived image afterwards. Files installed into mounted `/home/appuser` during an image build can be hidden by an existing volume; put image-owned tools under `/opt` or `/usr/local`.

## Publish from your fork

The `Build and publish LVK server image` workflow builds the root Dockerfile's `server` target. It uses `GITHUB_TOKEN` with `packages: write`, and publishes to `ghcr.io/<owner>/<repository>` in lowercase. Docker images are the only LVK release distribution; no npm publication or npm credential is required.

1. Merge tested changes into `main`; merging alone does not publish an image.
2. For an image-build rehearsal, manually dispatch the workflow on your branch. It builds and smoke-tests, and refreshes the build cache, but does **not** publish an application image.
3. At the chosen commit, create and push a version Git tag such as `v1.2.0` or `v1.2.0-rc.1`. The workflow strips `v`, builds the image, runs smoke tests, then publishes `:1.2.0` or `:1.2.0-rc.1`.
4. On the first publication, check the package's visibility and access under GitHub Packages. Make it public for anonymous pulls, or give users the appropriate package-read authentication. GitHub Releases need not be created.
5. Record the source commit and image digest from the workflow. Do not move/reuse version tags; the workflow intentionally does not publish a mutable `latest` tag. GHCR tags themselves are mutable, so pin deployments by digest when you require exact artefact identity.

The image carries OCI source, revision and version labels. See [GitHub's container publishing documentation](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) for registry permissions and organisation restrictions. A successful source merge or local test is not evidence that an image has been published: check the workflow result and GHCR package before telling users to pull it.

### Build cache

The workflow shares a registry cache at `ghcr.io/<owner>/<repository>:buildcache` across release tags. This tag contains build metadata and intermediate layers; use a version tag or application image digest for `LVK_IMAGE`. Workflow runs are serialised so concurrent releases cannot overwrite each other's cache exports. A missing cache causes a full build.

The Dockerfile uses a pinned `cargo-chef` to build Rust dependencies before copying the application sources and embedded frontend. Dependency artefacts stay in ordinary image layers so fresh CI runners can restore them. Changes to the dependency recipe or Rust toolchain rebuild that layer. The server's development tools are built independently of the LVK binaries, so application changes do not reinstall them. The lightweight `runtime` target remains available.

The first build after this change populates the cache and can still take a long time. To measure reuse, dispatch another build on the same commit and compare the build-step duration, then repeat after a normal source change. A same-commit cache hit does not measure Rust recompilation time. Check the dependency and tool-installation steps for `CACHED` in the build logs, and require the smoke tests to pass on each run.

## Validation boundaries

The kit includes Docker-free Node/Python tests for settings, IP certificate validation, atomic certificate export, reload retries, supervision, Compose/workflow structure and shell syntax; native nginx integration tests exercise TLS, Basic authentication, WebSockets, SSE and preview isolation. Rust and TypeScript tests cover public preview URLs and redirects.

```bash
pnpm run server:check
pnpm --filter @vibe/web-core exec vitest run src/shared/lib/previewProxyUrl.test.ts
cargo test -p preview-proxy
```

If nginx is not installed, the native test reports a skip. Use `LVK_TEST_NGINX=/path/to/nginx LVK_REQUIRE_NGINX_TEST=1 pnpm run server:check` to require it. The PR configuration workflow installs nginx and requires this test. The release workflow additionally tests the built image's tools, real LVK health/authentication, IP HTTPS, certificate reload without recreating LVK, and persistence across container recreation before pushing it.

<Note>
  CI uses disposable test certificates and does not contact a production ACME
  issuer. Verify real issuance, the renewal dry run and externally trusted HTTPS
  on your own public IP. Agent login and live execution require your own account
  and are separate from the container tests.
</Note>
