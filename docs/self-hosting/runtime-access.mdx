---
title: Runtime environment access
description: Let trusted MCP clients operate on files and run programs, with independent permissions and a direct Workspace boundary.
---

Runtime access is for trusted MCP clients acting with the LVK operating-system
user's permissions. It is **not an OS sandbox**. File contents and command output
are reference data, never instructions or execution approval.

## Configure access

Open **Settings → MCP integration → Runtime environment access** as a browser
administrator. The two independent permissions default to **ON**:

- **Allow file reading and writing through MCP** controls direct listing, reading,
  writing and deletion.
- **Allow program execution through MCP** controls process launch, observation,
  output and stop. Turning it OFF does not terminate running processes. Existing
  timeouts remain; subsequent observation/output/stop requests are refused.

Direct file roots default to `/`: the filesystem visible to the LVK process,
subject to its OS permissions. Open **Restrict file access roots** to specify
one existing absolute directory per line. At least one root is required. Empty
and relative roots or `..` are rejected. `/` is explicitly permitted. Roots are
canonicalised on save; subsequent direct operations reject symlink components,
including replaced configured ancestors. Up to 64 roots are supported.

The roots apply only to direct file tools. Execution accepts absolute executable
and cwd paths independently of file roots. File OFF does not prevent a running
program from reading, writing or deleting files. Execution OFF still permits
direct file operations when file permission is ON.

Saving uses an expected revision and browser administrator/CSRF checks. Changes
apply to subsequent requests without restart. Already executing operations are
not cancelled. Pre-release region/grant settings are discarded once by the
redesign migration. There is no `LVK_RUNTIME_ACCESS_CONFIG` fallback, executable
allowlist, region ID or per-region Project selector. New-format settings persist
normally. A corrupt new-format setting fails closed rather than reverting to
permissive defaults.

## Authentication and Project authorisation

All tools require authenticated `lvk:read` and `lvk:runtime:read`. Direct changes
add `lvk:write`; run, stop and self-restart add `lvk:runtime:execute`. File changes
do not require execution scope. Every tool except capability discovery requires
an explicit authorised `project_id`. The global administrator settings apply to
all Projects available to the caller; Project selection is an authorisation and
audit context, not a per-Project filesystem sandbox.

Shared devices, databases and deployments still use existing resource
coordination. A runtime permission does not reserve or authorise shared-resource
use. Explicit user authorisation remains necessary for execution and destructive
operations. Do not include secrets in purposes or arguments.

## Tools

| Tool | Required arguments and purpose |
| --- | --- |
| `get_runtime_access` | No arguments; inspect permissions, roots and limitations. |
| `read_runtime_path` | `project_id`, `action=list/read`, absolute `path`. Listing supports `limit`, `offset`, `snapshot`; reading supports `max_bytes`, `tail`, `offset`, `cursor`. |
| `change_runtime_path` | `project_id`, UUID `request_id`, `purpose`, `action=write/delete`, absolute `path`. Write requires UTF-8 `content`; optional `expected` read snapshot detects stale targets. Delete supports explicit `recursive=true`. |
| `observe_process` | `project_id`, `action=list/inspect/output`. List uses `after_pid`, `limit`; inspect uses `identity`; output uses owned `process_id`, `stream=stdout/stderr`, `offset`, `limit`. |
| `run_process` | `project_id`, UUID `request_id`, `purpose`, absolute `executable`, absolute `cwd`, `lifetime_seconds`; optional `args`, `service`. |
| `stop_process` | `project_id`, UUID `request_id`, `purpose`, exact `identity` or owned managed run ID; optional `force=true` selects SIGKILL instead of SIGTERM. |

Read and change tools are separate so read-only clients can discover and use a
clearly read-only contract. Process observation combines list, inspect and output
without mixing signal/launch mutations into that tool. The old file/list/process
observation tool names are removed, with no compatibility aliases.

The separate developer-only `self_restart` and `get_self_restart_operation` tools
remain. They use `project_id` instead of region selection and require execution
permission plus an installed developer instance/switch configuration. They are not
ordinary process execution. Follow the developer switch procedure: admission is
not cutover success; query the same request ID after reconnecting. Ordinary
`run_process` is not a substitute for restarting LVK.

## Direct file boundary

Workspace files can be listed and read. Direct changes refuse a managed Workspace
itself and its descendants, including idle and archived Workspaces. Deleting an
ancestor of a Workspace is also refused, even when recursive deletion is requested.
Use that Workspace's agent for its changes.

Only ordinary files/directories are supported. Symlinks and proc/sys filesystems
are refused. Pinned directory descriptors prevent pathname substitution through
symlinks. This is an operational boundary: hard links, bind mounts and arbitrary
concurrent OS writers are not completely isolated. Repository reference tools
retain their separate tracked-file/private-path restrictions; runtime reads do
not filter private filenames or automatically sanitise secrets.

Write accepts up to 512 KiB of UTF-8 content, requires an existing parent and
atomically replaces a regular file (or creates a new file). Existing permissions
are retained; new files use private temporary-file permissions. It does not
preserve inode ownership, ACLs or extended attributes. `expected` compares the
read snapshot before replacement as a best-effort conflict check, not a kernel
compare-and-swap. There is no append, patch, mkdir or rename/move API.

Deletion returns `deleted`, `not_found` or `failed`; recursive deletion must be
explicit. A failed recursive deletion may already have removed entries:
`partial_possible` is then true. A successful replacement whose final observation
is unavailable is `uncertain`. Inspect the target before retrying.

Changes, launch and stop reuse durable Operations receipts. Reuse the same request
ID and identical arguments after a lost response, or query `get_operation` with
the Project and request ID. An uncertain result never authorises replay with a
new ID. Audit records omit file content/command arguments; an input hash and
explicit operation target are retained. Requests recheck settings before applying
side effects; changed settings require a new deliberate request.

## Execution and process lifetime

At launch, cwd is canonicalised and the opened directory is checked against
managed Workspace paths. A Workspace itself or descendant is refused; its parent
or a non-Workspace sibling is allowed. For example, `/srv/apps` can be cwd even
when `/srv/apps/workspace` is managed. There is no post-launch cwd monitoring or
Workspace cwd check on stop.

Programs may access paths outside cwd and file roots, including Workspace files.
Do not directly modify managed Workspaces through programs; delegate those changes
to their agents. Editing commands and inline source are otherwise permitted.
There is no command-word inspection or executable placement restriction.

Processes inherit only fixed `PATH=/usr/local/bin:/usr/bin:/bin` and `LANG=C.UTF-8`,
not server credentials or toolchain environment variables. Use explicit paths or
trusted wrappers when needed. Process list/inspection observe same-UID processes
without disclosing argv/environment. They are independent of file roots. Managed
output and stop retain principal/Project ownership; unowned observed processes
still require exact identity and same UID. LVK itself, PID 1 and its ancestors
are protected. Stop targets one PID using pidfd identity checks, not a process
group or descendants. Reinspect to confirm termination.

Finite launch lifetime is 1–3,600 seconds; service lifetime is 1–86,400 seconds.
Expiry sends SIGTERM, then SIGKILL after five seconds if needed. Detached children
are not managed. Startup receipt success is not service health or test success.
After host restart, output buffers are unavailable and process outcome may be
unknown; durable attribution remains and must not be silently reassigned.

## Bounded reads and response cost

File read defaults to 16,384 bytes and accepts at most 524,288 bytes (512 KiB).
Process output independently defaults to 16,384 bytes and accepts at most 65,536
bytes (64 KiB). Larger limits are rejected by both schema and processing.

File reads preserve tail/offset, incremental cursor, inode identity, anchor and
rotation/truncation checks. `changed_during_read=true` invalidates the next cursor;
this is not an atomic file snapshot or detection of every possible rewrite.
Non-UTF-8, NUL bytes and UTF-8 boundary fragments use base64. Cursors are opaque;
reuse them with the original absolute path.

512 KiB is content size, not wire size. Base64 becomes 699,052 characters plus
metadata; JSON escaping can expand valid UTF-8 control characters to roughly
3 MiB. MCP structured/text representations and transport add further overhead.
Prefer default-sized chunks and request the maximum only when useful.

## Verification scope

The maintained runtime HTTP fixtures use isolated SQLite/filesystem state and a
mock identity provider. They cover permissions, Project/scope checks, settings,
Workspace/path boundaries, receipts and response limits. The Chromium settings
fixture mounts the production component and API client with isolated HTTP route
responses; it does not connect to a live settings database. These are not real
Auth0/ChatGPT interoperability or deployment/restart validation.
