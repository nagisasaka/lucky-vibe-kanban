title: "Astra project conversations"
description: "Discuss a project and delegate normal LVK work from a persistent server-side conversation."
---

Open a local project and select **Astra**. Select **Board** to return to the
existing kanban. Issue details, Workspace sessions, approvals and diff review
remain available through the work links below the conversation.

## Configure the server

Astra uses the **ChatGPT login managed by Codex on the LVK server**. Run
`codex login` as the same operating-system user, in the same container and with
the same `CODEX_HOME` as the LVK process, and choose ChatGPT sign-in. An existing
ChatGPT login can be reused. You do not need an Astra API key or a separate
Astra sign-in. Codex manages credentials and token refresh; LVK never copies
those tokens into its settings or chat history.

Set `LVK_ASTRA_MODEL` in the server process environment to the model you want
to use, for example `gpt-6-astra`. The model must be available to the signed-in
ChatGPT account. Reasoning effort defaults to `xhigh`; override it with
`LVK_ASTRA_REASONING_EFFORT`, or save model preferences through
`/api/astra/settings`. Environment changes require a server restart.

Astra requires Codex 0.154.0 or newer, with App Server ephemeral threads,
environment selection and structured turn output. It checks for a
ChatGPT account and does not fall back to API-key authentication. Without a
ChatGPT login, conversations remain saved and the chat shows sign-in guidance.
Login availability is cached for up to 15 seconds. A successful account check
does not verify model access or remaining usage; failed turns remain queued
with the existing retry policy.

Each inference runs in an ephemeral Codex thread with no execution environment,
with inherited MCP servers, plugins, shell tools and skill instructions disabled.
Codex returns a structured reply or a proposed LVK operation. LVK saves that
proposal before executing it through the existing project-scoped permission
checks and durable receipts. Astra's conversation history stays in LVK.
Legacy saved Astra keys are preserved until explicitly cleared, but are not
used. New API-key values are rejected.

See the official [Codex App Server authentication documentation](https://learn.chatgpt.com/docs/app-server)
for managed ChatGPT login and token refresh.

Implementation needs a repository associated with the project through the
existing Git working-location default, repository binding or a linked Workspace. Astra cannot choose an
unrelated host repository or create repository permissions.

The normal database migration adds conversations, messages/checkpoints,
tool receipts, a small event outbox and shared asynchronous-question answer
receipts to the existing SQLite database. Back up the normal LVK data volume
before upgrading. No extra database or message broker is needed. Run one LVK
server process per database, as for the existing local runtime monitors.

## Send requests

Choose one of two modes in the composer:

| Mode | Authority |
| --- | --- |
| 相談／RO (read-only) | Read state, code, Memory and Wiki and discuss options. Changes are rejected by the server. |
| 操作可 (operations allowed) | Carry out your current direct request through existing LVK operations. Consultation alone causes no changes. |

The default is RO, including requests that omit the mode. Select 操作可 explicitly
and send a new request when you want changes. Natural language cannot switch
modes. The selection lasts while this project's chat stays mounted; reopening,
reloading or switching projects resets it to RO. A polling reconnect preserves
the current selection. Each submitted message keeps its original mode and local
conversation owner; later changes never expand an earlier message's authority.

In 操作可, ask naturally: “Leave this as an Issue” creates only an Issue;
“Implement this” creates a self-contained Issue if needed and starts its Workspace.
“Change that implementation” steers or continues the identified Session without
editing Issue requirements unless you request that edit. Answer a pending
specification question or request a merge through formal Integration in the same
mode. Astra checks current targets and asks for clarification only when necessary.
The chat question panel also requires 操作可 before sending an answer.
Execution tool approvals remain in the existing Workspace approval UI. These
chat modes do not change Workspace Codex modes or approval policies.

Saved legacy request types and in-flight checkpoints retain their original narrow
permissions; they are never converted to 操作可. Internal tool names and receipts
continue to identify the individual operation. No history migration is required.
If message delivery is unconfirmed, retry the frozen message, mode and request ID
before editing the composer; this avoids submitting the same request under a new ID.

An implementation receipt names the accepted Issue/Workspace/run. It does not
mean implementation, tests or merging have completed. You can immediately send
another message while the existing server-side agent runtime continues.
Multiple attempts remain separate Workspaces; the chat adds no agent scheduler.

## Questions, direct intervention and results

Important runtime events are stored with their original IDs in the same
transaction as the underlying event. They are batched into read-only conversation
turns. Token updates and individual command-output lines do not trigger inference.
Direct Workspace instructions and answers are included, not just Astra's work.

Blocking input questions retain their run and input IDs. Codex nonblocking
questions retain attempt/message/question IDs and original options. The
Workspace question UI and Astra share server-side answer receipts. A direct
answer prevents another answer from being sent through Astra. Older clients'
canonical `Question: … / Answer: …` inputs are also checked. A pending command
is an accepted submission, not evidence that the agent has incorporated it.

Before a change or answer, Astra reads the current Workspace revision. A
revision conflict requires reconciling intervening instructions. It does not
silently overwrite the user's direct input. To inspect implementation evidence,
Astra can read canonical final responses, branch status, tracked reference
files, Workspace memory, manifests and the existing OpenWiki snapshot.

Merging uses existing Board Integration admission, reservations, source checks,
validation and publication. Integration considers the complete selected commits and
their frozen public Change Manifests, including follow-up work absent from the
original Card description. Such omissions alone do not block merging. Private
Workspace memory and raw conversations remain outside this shared context.
Its receipt is only admission. Integration status,
test evidence, publication and OpenWiki receipt remain separate observations.
The retired generated LLMWiki pipeline is not restarted by this feature.

## Reconnection and recovery

The browser polls persisted results while visible. Closing it does not stop
either the conversation worker or delegated agents. Another device using the
same local LVK identity loads the same conversation. Responses are displayed
when a model round completes; this version does not stream individual tokens.

Without model configuration, messages and events stay saved. Transient model
failures retry with bounded backoff. Coding agents continue independently. A
conversation has one active model turn, while different conversations and
ordinary Workspaces can progress independently.

Model tool calls are checkpointed before execution and results before replay.
On restart, existing Issue, command, run and Integration identities are checked.
If a side effect cannot be confirmed, Astra reports an uncertain result and
does not blindly replay it. Inspect the named Workspace/Session/Integration
before issuing a new instruction. A server restart preserves records; it is
not by itself proof that an operating-system process survived.

## Initial scope and limits

This is the local single-user server feature, with one named conversation per
project and local owner. Conversation identity is separate from project state;
multi-user/remote-cloud conversation authorisation is not implemented. The
existing single-user server access boundary still applies.

Model input uses recent conversation messages and current shared state; full
history remains in SQLite. A model can page through older conversation messages or request more Workspace detail instead
of receiving every execution log. Older conversation messages remain reference context; only the current request
grants authority to operate. The UI provides polling rather than a
new streaming transport. External model quality and actual Codex execution
require separate live validation; deterministic tests use substituted clients.

## Development checks

Run `cargo test -p server --lib project_chat` for the conversation tests. They
use the real SQLite migrations and canonical runtime records with a substituted
model/execution boundary. Assertions cover capability limits, project isolation,
question identity, direct answers, persisted event cursors and interrupted tool
receipts. Two-mode tests cover all existing write tools under 操作可, RO/event rejection,
legacy checkpoint ceilings, Issue-to-Workspace identity and partial success.
Scripted mock model responses test dispatch and side effects, not live natural-language accuracy.
Run `pnpm run chat:test` for the isolated browser regressions, including mode
reset, polling and immutable retry identity. Run `cargo test -p server --lib` to include existing Integration tests
with temporary Git repositories. The full server suite also tests static file
serving and requires the local Web build in `packages/local-web/dist`.
Use the existing Dockerfile's `NODE_OPTIONS=--max-old-space-size=4096` when
building the local Web bundle outside Docker as well.

The browser regression is `tests/server/specs/project-chat.spec.ts`. It mounts
the real chat component on a disposable Vite development server and intercepts
its APIs. Set `LVK_E2E_BASE_URL` to that server and `LVK_E2E_SOURCE_ROOT` to the
absolute repository path, then run
`pnpm exec playwright test -c tests/server/playwright.config.ts project-chat.spec.ts`.
It checks saved history, continued conversation during execution, exact question
answers and navigation to existing work. It does not invoke OpenAI or Codex.
