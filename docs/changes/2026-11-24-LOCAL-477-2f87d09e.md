> 当時の意図を示す資料であり、現在の仕様・実行許可・実装完了の証明ではない

結論：LVK の共有 dev だけ、フロントの Vite ビルド済み dist と Rust バックエンドを個別に更新可能にする。preview2 は作業ツリー＋HMRのまま、安定版は現状の埋め込み単一リリースのまま。共有 dev に Vite 常駐/HMRや別配信サービスを追加せず、既存 Rust server が dev 専用の外部 dist を同じ origin・認証境界で配信する。

背景：LOCAL-475 はフロントしか変更していないのに従来 dev ビルドで Rust 3バイナリに9分、全体13分23秒。単にコンパイルを速くするのではなく、変更していない側を再ビルド／再起動しない。LOCAL-454 は既存の切替用ビルド経路と検証の参考であり、本件は別の製品変更。既存の公式 developer-runtime・切替ツール・マニフェスト・ヘルス・ロールバックの仕組みをまず読んで使い、二重実装や不要な新 MCP／デーモンを避ける。

合意仕様：
- フロントのみ：対象コミットの dist をビルドし、検証後に完成済みアセットを一式として原子的に切り替える。稼働 server/agent host/MCP を再起動・再ビルドせず、DBやRunに触れない。旧 index を持つタブのハッシュ付き chunk を切替直後に壊さない方法と、旧 dist を使ったロールバックを最低限用意。無効な配信物を有効化しない。
- バックエンドのみ：依存関係・ビルド入力が影響を受ける Rust バイナリのみ更新。影響がない実行ホスト・stdio MCP は適合する成果物を再利用可。稼働 dist は据え置き。必要なバックエンド再起動は既存の安全な切替手順とヘルス検証を守る。無理な成果物再利用より確実なビルドを優先。
- API・共有型・生成物・共有依存や変更範囲の判断が曖昧な場合：フロントとバックエンドを同じ対象コミットから用意し、互換性を維持する一組として切替／ロールバック。巨大な自動分類は不要。入力と判断根拠を明示し、不明なら両側。
- dev の稼働情報には実際のフロント SHA とバックエンド SHA を別々に示す。両者が異なるのは正常。同一コミットと偽装せず、再利用した補助バイナリの由来は必要に応じ manifest に残す。安定版は既存の単一 SHA と埋め込み配信を変更しない。preview2 の HMR・認証も変更しない。

検証：隔離の dev 相当で A→フロント B（PID/バックエンドSHA不変、新画面と配信アセット・既存タブのリクエスト・ロールバック）、次にバックエンドのみ（フロント SHA と dist 不変）、必要な両側更新、無効物・切替失敗時の既存稼働保持、既存埋め込み経路の回帰。API・WebSocket・MCPと認証境界に回帰がないことを、変更に見合う試験で確認。測れるなら各経路でビルド・切替時間を別記。実機未確認は明記。
コード・隔離試験まで。稼働 dev/stable/preview2、実 DB、認証設定、既存Run、GitHubへのpush、main マージには触れない。生成物は Workspace ルート .lvk/local。実際の放出手順、既存運用からの移行方法、未検証点を日本語で報告。
