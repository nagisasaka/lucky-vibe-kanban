## 結論
Codex がネイティブサブエージェントに fan-out した Run で、子が終了済みなのに LVK が未終了・不明と判定して Run を失敗にする経路を確認し、修正する。子が実際に動いている、または完了証跡がない場合の保護は維持する。

## 観測と調査の起点
- LOCAL-460 の親 Run `7c2d008a-baf0-44dc-bd08-1a2907799b72` は 2026-11-23 08:51 UTC にネイティブ Goal 完了の後、`Codex parent completed while a sub-agent was still running or its completion was unknown; refusing successful Run completion.` で失敗した。UI では provider executor reported failure。以前の LOCAL-463 にも類似表示があったが同一原因とは未確認。460 に紐づく別 Workspace の 466–468 の成功履歴は、Codex ネイティブサブエージェントの終了証跡とは別。
- main `200a7669` の `crates/executors/src/executors/codex/client.rs:2037–2117` では、collab tool item の receiver 一覧だけで既存終了証跡を無効にし、その item の明示状態だけで上書きする。観測のみの wait でも V1 形式の receiver ID＋空の状態 map を受けると終了が未確定へ戻り得る。一方 `agent_scope.rs:86–100,413–425` は状態のない wait を観測としている。現行 V2 のイベント形状も確認し、V1 と混同しない。460 の公開イベントではネイティブ ID と生フレームが揃わず、上記は有力な候補であって 460 の実トレース原因は未確定。
- 関連：LOCAL-4（元の可視化と終了ガード、マージ済み）、LOCAL-460（発生例）、LOCAL-461（ゴールの委任標準化、別目的）。

## 実施と受入
1. 実際に使われている Codex/App Server 版とイベント形式を確認。観測・再開・明示 lifecycle の扱いを突き合わせ、確認できた誤判定を最小差分で直す。終了ガード撤去や親の Goal 完了だけで成功に倒す対応はしない。460 のイベントが取得できない場合はその限界を報告し、確認済みの欠陥と分ける。
2. 回帰試験：終了済み A → A/B の状態なし grouped wait start → B のみの端末状態を返す wait → A の終了証跡が維持され、全員終了なら親を誤失敗させない。対照：A の実際の resumeAgent／稼働を起こし得る sendInput 後は新しい終了証跡まで未確定、実際に動作中・状態不明の子がいるケースは成功扱いしない。現行形式と対応中の legacy 形式を必要な範囲でカバー。テストは合成イベントまたは許可された隔離環境で行う。
3. 可能なら隔離した小さな Codex Goal でネイティブの fan-out → wait → 親完了まで再現し、LVK Run の最終状態と通常の成果記録まで確認する。環境依存で実機確認できなければ、実行した試験と未確認事項を明記。
4. 460 や既存 Run の変更・再実行なし。現行 dev/stable の操作、main マージ、公開なし。報告は日本語で、原因の確度・差分・テストを簡潔に分ける。
