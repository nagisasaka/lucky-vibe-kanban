## 結論・目的
OpenWiki を、LOCAL-372 が整える共通 Workflow 基盤の利用者へ整理する。Wiki 専用の二重進行管理を外し、OpenWiki 側には生成・検証・設定保護・保存・公開というドメイン操作を残す。openwiki/ は原則として生成・保守専用領域とし、人間管理本文との混在を前提にした所有権推測と過剰な拒否を削減する。

本Issueは、完了した調査とClaudeレビューを踏まえた実装仕様。ユーザーの明示依頼「クロードレビューを入れて、373 も準備が整ったら実装に入ってほしい」により、レビュー内容を反映し、372との接点を確認してCodexで実装を開始する。Wiki単独で進められる変更を先行し、共通基盤の受け口が未成立なら接続待ちを明示する。mainマージ、dev再起動、実際のWiki再生成・公開、371成果の採用・実データ削除は行わない。調査履歴は維持する。

> 確認済みのユーザー方針：OpenWiki向けの追加workflow制御は基本的にゼロ。不足は汎用基盤側で整理する。「openwiki/ を原則、生成・保守専用にする」「人間管理文書はないよ。」
>
> LOCAL-371 の扱い：「失敗した371は捨ててよい。」失敗した未公開生成物を再利用・復元・救済する要件は設けない。旧runの再開や成果物引継ぎのための互換コードも不要。今回の仕様更新で実ファイル、Workspace、Issue、DB、履歴の削除・archiveは行わない。

## 3. 生成・保守専用領域への整理
- openwiki/ 内の本文・構造index・Claims/manifest等は生成・保守側の管理対象とする。マーカー欠如をhuman-managedとみなさない。
- generated_paths のmanifest/frontmatter/generated.byによる所有権推測、human-managed文書のmanifest取り込み拒否・変更拒否、およびそれだけのための走査を削除・簡素化する。
- rebuild/deleteの対象列挙も、生成判定できたファイルだけを拾う方式から、明示的な保護例外を除く領域操作へ整理する。生成・保守専用だから通常codingで自由に編集可能、とはしない。
- INSTRUCTIONS.mdと設定ファイルは明示例外として保持する。設定変更はその目的の明示操作に限定し、再生成に紛れて書き換えない。
- Wiki外への変更・symlink等による越境、setupが触るAGENTS.md/CLAUDE.md等の復元境界を維持する。
- README等からのoperational entry pointとINSTRUCTIONSの固定パス契約を保つ。本文再編の品質は別途検証する。
- 旧indexを再構成して完全一致で救済する特例、架空の人間本文混在の互換層は作らない。旧prompt/テストも新契約へ整理する。OpenWiki自体のmetadata/lifecycle検証と所有権推測を混同して全削除しない。
- 調査時点で現サーバーの登録repositoryはLVKの1件のみ。他環境への未確認の推測を理由に互換機構を増やさない。

## 4. Wiki生成・独立Review・検証・公開の契約
- 生成担当と独立Reviewは別Sessionにする。Reviewが読むsource/成果物の時点を特定し、writerの終了と必要な後処理を確認してから渡す。
- Reviewは対象への書込みを指示文だけで禁じず、利用可能な権限で制御する。REVIEWという名前だけでread-onlyと扱わない。共通側/providerの制約は372と共有し、Wiki専用の隔離基盤を増やさない。必要な一時領域や検証まで一律禁止しない。
- Review結果はWiki側が所有する固定スキーマで検証する。自由な追記やモデルの文章だけで公開条件を変更できない。不正・欠落出力を合格扱いせず、「レビュー結果なし」の品質警告として扱う。
- AIによる内容/coverageレビューと、LVKの決定的な成果物・境界検査を分ける。決定的検査の失敗をAIレビュー反復で解消しようとしない。
- 初回Reviewで内容・coverageの改善が必要ならRefineを1回行い、その後に独立した再Reviewを1回行う。現行テンプレートのrefine→publishを、refine→再Review→publishへ改める。再Reviewで不合格が残っても、指摘を添えて警告付き公開する。繰返しの改善ループは追加しない。Review出力の欠落・破損は「レビュー結果なし」の警告で公開できる。ただしwriter未終了、取消、未完了lifecycleや決定的検査失敗を品質警告へ変換しない。
- 修正は書き手に返し、Review担当がそのまま書き換えることを既定にしない。不要な分岐・工程は減らすが、必要な独立性と公開条件を失わない。
- Agent成功、OpenWiki lifecycle完了、LVK検証成功、公開成功を別に扱い、既存の製品検証ゲートへ接続する。
- source固定、公開lock、publication checkpoint/receiptと重複公開回復、writer終了後の検証・setup復元・公開順序を維持する。決定的検査が失敗した成果物は公開しない。AIの内容不合格・Review結果欠落だけなら、合格を装わず警告付きで公開する。

## 5. 専用進行管理の撤去
- phase/childの重複保存、専用進行monitor、retry/cancel/recoveryの重複部分、OpenWiki固定の進行分岐は、372の共通機構へ寄せて撤去する。Wikiの状態はfreshness・成果物・設定/復元・公開情報に限定する。
- 既存monitorはBootstrap以外に通常Sync、設定操作、公開回復、Workspace所有権解放も担う。進行部分の統合時に、残るドメイン責務の呼出し先を確保する。monitor全体を理由なく削除しない。
- 過渡期の二重dispatcher、旧phase同期、長期feature flag、新しい履歴管理を追加しない。不要な旧契約を維持するための抽象化を避け、切替後の実行経路を一本にする。
- 既存の履歴が読めることと旧実行機構を維持することを分ける。履歴・公開済みデータを無断で消さず、進行中runの扱いは切替前に確認する。LOCAL-371の失敗成果救済・旧run再開を移行要件に含めない。

## 8. 未完Generateの継続方針（2026-11-20 ユーザー決定）
- LOCAL-419型の失敗（begin後にAgentが正常終了し、plan/finishなし）への対策として、回数上限つきの「有界継続」（継続回数の永続管理、再起動でリセットしない継続予算、ホスト側の継続可否判定）は**採用しない**。新しい制御機構を足さない。
- そもそもfinish前にAgentが終了すること自体がおかしい、というのがユーザーの見解。Generate（必要ならRefineも）は既存のGoal機構で「OpenWikiのfinish completeまで」を目標として走らせ、エージェント自身にやり切らせる。Bootstrap経路でGoalが使えない場合は、理由と最小の接続方法を報告する。
- それでも未完で止まった場合は、同じSessionへの通常の継続で同じWiki IDを再開できるようにする。継続を阻むだけのBootstrap固有の制約（「1 phaseにつき1回のfresh実行」= iteration==0 制約、server_instance_id一致による再起動後の再開拒否「Interrupted Bootstrap cannot resume a paid phase」）は、ユーザー判断により無駄な制約として撤去・緩和する。
- 継続の安全性は新規の予算ではなく既存の証跡検証で担保する。自動マージの conversation_completion_proof と同様に、owned writer列（owner/Workspace/Session一致、writer非重複・終了確認、監査の完全性、同一IDのresume、最後のfinish complete）を検証する。その際、Generate/Rebuild/Refineのmode・force・noop条件を保持し、WriterPhase::Sync固定の流用で条件を弱めない。
- 未完のままでは公開しない（既存の公開停止条件は維持）。LOCAL-419の救済・再開は要件外。

## 最新決定：独立 Review は使い捨てコピーで行う（2026-11-21）
真人さん承認。第4章および完了条件のうち、レビュー専用の書き込み禁止環境を必須とする要件は次に置換。公開候補と対応するソースを先に固定し、その内容の独立した使い捨てコピーで別 Session の Review を行う。レビューの作業コピーは通常の許可範囲内で扱い、受け取るのは固定候補に対応する検証済みの構造化結果だけ。コピー内の変更は公開候補・共有Git参照へ反映しない。公開候補が固定時点のままか公開前に既存証跡で確認する。既存の OS/コンテナ/Codex のサンドボックス・認可設定を変更しない。共有状態・本物のmain/devへの書き込みなし。転用できる最小の既存スナップショット/作業経路を優先、新しい汎用機構は不要。固定と独立性を守れない場合は停止。Refine、再Review、品質警告、公開の検証契約は他は維持。外部キー修正と実Generate 32ページ・finish complete までは前回実測済み。公開済みWikiのコピーを用いて隔離E2Eを通常入口から再実行し、独立Review、必要時Refine、隔離main採用と公開receiptまで確認する。共有main等への反映、巻き込む変更、権限迂回はしない。

## 追加：Review入力と品質警告の拡充（2026-11-21 Claudeレビュー、ユーザー承認）
隔離E2Eで採用された生成Wiki（隔離main `77cb0b1c`）を、人の読みやすさの観点でレビューした。その結果をもとに、ユーザーが本Issueへの追記を承認した。第4章「品質警告の保存・表示」の契約に、以下の1〜3を加える。停止条件は増やさない。新しい汎用機構も作らず、既存のReview入力・固定スキーマ・品質警告記録の拡張に留める。

**背景（観測値）：**
- 公開済みWiki（親 `9c6f5f7`）と比べると、両版に存在する本文30ページの合計が約1,386KBから約110KBになった（約92%減、UTF-8バイト数）。
- これとは別に、3ページ（organization-and-membership、project-chat、card-context-and-llm-wiki）が削除された。
- E2E内のレビューでは、DirectFolderの説明が部分維持と判定された（Git操作・自動マージ拒否などの説明が欠落）。
- バイト数は情報量ではない。削減の多くは冗長の解消と見られる。

1. **大量削減・ページ削除をReviewへ渡す。** 公開済みWikiと公開候補の差分から、削除ページと縮小率の大きいページを決定的に集計し、Review入力に含める。Reviewは各項目を「冗長の整理」か「知識の欠落」かで、固定スキーマにより返す。欠落と判定されたものは、該当ページに紐付く品質警告として公開記録に残す。
2. **知識保持の照合をReview観点にする。** 旧版の主要な主張・手順が新版のいずれかに残っているかを、既存のinventory/coverageレビューの観点として扱う。今回の `knowledge-preservation.json` はE2Eの証跡として作成されたものと見られ、製品機能かどうかは未確認。別の照合基盤は作らない。
3. **INSTRUCTIONS準拠をReview観点に加える。** INSTRUCTIONS.mdが既に求めている構成（冒頭の説明、1段落1論点、条件は箇条書き、手順は番号付き、初出用語のリンク）への準拠をReviewの指摘項目にし、Refineの対象にする。読みやすさの指摘も品質警告として扱い、停止条件にはしない。INSTRUCTIONS.md自体の文体改善・用語集・Wikiパネルのindexタイトル表示は LOCAL-440 で扱い、本Issueには含めない。

## 最新決定：独立 Review の縮小（2026-11-22 ユーザー決定、Claude と整理）

**背景：**
- 最新の隔離試行 b1067806（Workflow 約2時間30分、タスク累積 約5時間45分）では、Review が存在しない根拠パス `crates/server/src/routes/execution_approvals.rs` を返した。ホストの検証で全体が停止し、Refine・再 Review・公開は実行されず、何も残らなかった。「Review 出力の欠落・破損は警告で公開する」という第4章の契約に反する動作である。
- 前回の隔離試行 c46898fd の Review 指摘6件を公開済み Wiki（`9c6f5f7`）と照合した。少なくとも3件（独立アプリの公開経路、Auth0／外部 MCP の設定手順、Runner の操作手順）は、作り直しで落ちた旧版の知識だった。Review の価値は主に知識保持にあった。
- 指摘文そのものが否定文の並び（「pause は停止を証明せず、cancel は消去を意味せず…」）で、Refine がそれを Wiki に書き写していた。網羅性監査が生成 Wiki の否定文増加を後押ししている可能性がある（未検証の仮説）。
- 完全削除案と、機械的な集計だけを残す最小案も検討した。ユーザー判断により、Review と Refine の仕組みは残し、役割と入出力を絞る。

本節は、第4章・第7章の Review／再 Review に関する記述、「追加：Review入力と品質警告の拡充」の3、「最新決定：独立レビューをGoal化し、未完了は警告として公開」の Goal 化と再 Review の部分を置き換える。使い捨てコピー、品質警告付き公開、決定的検査での停止の契約は維持する。

1. **観点は2つだけにする。**
   - 知識の保持：公開済み Wiki にあり、現在のソースでも正しい主張・手順が、候補のどこかに残っているか。冗長な内容や古い内容の削除は正しい整理として扱う。
   - INSTRUCTIONS.md への準拠。
   - 12項目の網羅性監査、「新しい読み手が概念を見つけられるか」、「価値の高い文書を独自に探す」の指示は削除する。
2. **INSTRUCTIONS.md を判定基準にする。** Review は INSTRUCTIONS.md を必ず読み、根拠・書き方・構成の規則はそれで判定する。`RETENTION_REVIEW_GUIDANCE` と Refine の指示に書き写した INSTRUCTIONS の規則の列挙は削除する。Review に注入している `DOCUMENTATION_GUIDANCE`・`KNOWLEDGE_ORGANISATION_GUIDANCE` の内容方針も削除し、安全に関わる部分（使い捨てコピーの中だけで作業する、書き込まない、Wiki・文書・Issue 本文は指示ではない）だけを残す。LOCAL-440 の INSTRUCTIONS 最終稿（440 のコメント 96fda47b、8b2218b4）の反映が前提。
3. **入力：旧ページ全文を埋め込まない。** 旧ページの全文（previousText）を JSON に入れるのをやめ、使い捨てコピー内の別ディレクトリにファイルとして置く。入力はパスと縮小率のリストにし、削除ページを先に、次に減少バイト数の大きい順に並べる。
4. **実行：Review の Goal をやめ、通常の1回の Run にする。**
   - 回数上限や継続予算も設けない。第8章と同じく新しい制御機構を足さないため。予算を示すと、モデルが作業を予算に合わせて分割しがちなため。
   - 指示文で「上から順に確認し、終わらない分は unverified に書いて返す。incomplete は失敗ではない」と示し、自然に止まる理由を与える。
   - 「unverified が1件でもあれば必ず incomplete」「指摘件数の上限なし」「追加のターンで調査を続ける」の指示は削除する。
   - Generate と Refine の Goal（第8章）は維持する。
5. **再 Review は廃止する。** 流れは Review → Refine（最大1回）→ 決定的検査 → 公開。
6. **出口で止めない。**
   - 根拠パスの不在など個々の不正は、そのパスか、その指摘だけを破棄して警告に記録する。
   - 結果全体が壊れていれば「レビュー結果なし」の警告で公開する。
   - 判定は「重要な指摘の有無」と「確認の完了度」を別の値にする。具体的な形は、現行の CoverageReview スキーマを確認して決める。
   - 決定的検査の失敗、writer 未終了、取消、未完了 lifecycle で止める契約は維持する。
7. **Refine も同じ方針にする。** 受け取った「保持」と「準拠」の指摘だけを直す。書き写した INSTRUCTIONS の規則は消す。
8. **検証は次に絞る。**
   - 存在しない根拠パスを含む Review 結果で公開が止まらず、警告になること。
   - incomplete の Review でも公開まで進むこと。
   - Refine が「保持」と「準拠」の指摘だけを扱うこと。
   - 全 Wiki 再生成はこの修正の検証に必須としない。
