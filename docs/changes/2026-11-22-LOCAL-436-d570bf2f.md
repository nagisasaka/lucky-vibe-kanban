## 目的と判断理由

- 「カンバンボードを見渡せばだいたい分かる」程度の協調を基本とし、まれな共有 DB や将来の実機利用のために、独立した重厚な共有資源管理基盤を保持しない。普段の開発を素のコーディングエージェントより不自由にしない。
- 上位 AI が remote MCP でホストへ直接アクセスする経路の規則を、stdio MCP や Workspace エージェントのネイティブな調査・編集・実行へ広げない。LVK 管理操作の意味を共有することと、ホスト操作の公開範囲まで同じにすることは別である。
- 現行 Runner は資源登録だけでなく、配送・停止・完了確認・復旧まで汎用資源基盤に結合している。今回は併せて廃止し、Runner を残すための代替ライフサイクルを新設しない。将来の THINKLET 等に向けた Runner の新設や再設計は本 Issue の範囲に含めない。
- 複数 Workspace が同じテスト DB を共有する場面はあり得るが、現段階ではレアケースと判断する。環境を分けるか作業順序を調整する運用を基本とし、全プロジェクトへ資源登録を要求しない。
- 並行作業は既存の Issue／Workspace／Session／Run、カンバン、parallel context、Manifest を使って把握する。原子的な予約・排他やホスト全活動の完全把握ではないことを認め、管理状態・指示・保守対象を減らす。

## 削除・維持する範囲

| 対象 | 確定方針 |
| --- | --- |
| 任意資源の登録、利用権の一括取得、待機・AI 調停、汎用の状態 revision／所有権／復旧 | 廃止する |
| 上記専用の設定 UI、REST／MCP、型、ガイド、注入指示、テスト、文書 | 本体と合わせて削除・修正する。画面だけ隠して機構や制約を温存しない |
| 現行 Runner／execution bridge | 登録・認証、source snapshot、配送、command／settlement、停止・復旧、クライアントスクリプト、専用型・テスト・文書を含めて廃止する |
| 上記廃止機能に属するデータ・履歴 | 保持不要。退避先や互換機構を設けない |
| カンバン、Issue／Workspace／Session／Run、parallel context、Change Manifest | 通常の作業把握・継続・記録として維持する |
| `.lvk/shared/tmp`・`cache`・`persistent` | ファイルの受け渡し・再利用・保持という独立した共有ストレージ機能として維持する |
| Git・DB・自動マージ等の各機能自身の整合性を守る制御 | 維持する。資源管理固有の依存だけを外す |
| CPU・メモリ等の resource_observation、OAuth の resource 概念 | 汎用共有資源管理とは別機能として維持する |
| remote MCP の汎用ホスト直接操作 | 外部上位 AI 用の公開範囲と規則として維持し、廃止した資源管理を前提とする説明を修正する |

代替の汎用ロック基盤、資源スケジューラ、全ホスト監視、AI による自動危険検出を新設しない。同じ管理を別名で再構築しない。全コマンド前のボード確認、利用宣言の記入、他エージェントの承認待ち等も必須プロトコルにしない。他の作業や共通環境へ影響する場面で、既存の活動情報を判断に使えばよい。

## remote／stdio と共通 Skill の整理

1. 外部上位 AI の remote MCP による直接ホスト操作と、担当エージェントへ依頼する通常経路を区別する。remote の直接操作規則は、担当者を経由せず操作するときの API レベルのガードと運用規則であり、OS sandbox や上位 AI の総能力を封じる仕組みではない。
2. Workspace の担当エージェントは、依頼された範囲と既存の OS・コンテナ・ハーネス権限の下で、ネイティブな読み取り・編集・shell／実行ツールを使う。ローカル作業を remote 用ホスト操作 MCP へ通すことや、汎用資源の登録・利用権取得を要求しない。
3. stdio MCP は LVK の管理機能との連携に使う。削除するのは資源管理・現行 Runner の機能であり、stdio MCP 全体ではない。調査時点では汎用ホスト操作 API は remote 側にあり、同じホスト操作を stdio から削除する実装は確認されていない。存在しない公開実装を削除対象として作り出さない。
4. Skill の正本は共通のまま、共通規則・外部上位 AI・Workspace 内担当エージェントの適用主体と経路を明記する。参照文書、注入文、オンデマンドガイド、MCP metadata、配布先も同時に整え、資源登録を通常作業へ強制する指示を残さない。Skill を二重管理しない。
5. file roots は直接ファイル API 用であり、`run_process` のプログラム全体を閉じ込める保証ではない。指定ディレクトリ外への全アクセスを技術的に防ぐと説明しない。新しい OS 隔離機構の実装へ広げない。

## データ廃止とスキーマ移行

- 共有資源管理・Runner 専用の既存データと履歴は削除対象であり、保存・退避・エクスポート・移行先を用意しない。「実データがあるかもしれない」を理由に保持方針を再び未決に戻さない。
- 調査時点の対象は `shared_resources`、`resource_operations`、`resource_holders`、`resource_events`、`resource_mediations`、`bridge_runners`、`bridge_sources`、`bridge_commands`、`bridge_settlements`。最新 main で実際の依存と廃止範囲を確認する。
- 過去の SQL migration は適用履歴として保持し、後続 migration で対象テーブル・データと依存する外部キー、削除／archive 防止 trigger、CHECK 制約等を整理する。過去 migration の保持は、旧機能や対象データの保持を意味しない。
- 資源調停専用の Workspace／Run／owner 分岐、実行理由等も整理する。通常の Issue／Workspace／Session／Run／Manifest を一括削除せず、残す機能の参照・終了処理・cleanup の整合性を保つ。
- 不要な互換 API、fallback、機能フラグで残す旧実装、長期の二重運用は追加しない。

## 実装で追う依存と変更範囲

1. **資源管理本体と起動時処理**：DB モデル、サービス、queue、実行・検証・調停・再起動後の復旧、startup monitor、専用 `ResourceCommand`／`ResourceMediation` の型と分岐を整理する。
2. **公開面と生成物**：専用 REST／stdio MCP、設定 UI、API client、i18n、設定 registry、型生成と生成型、専用テストを一緒に削除・更新する。
3. **Auto-merge**：`guard_workspace_idle` の資源操作照会を外す一方、AgentRun、実行プロセス、未確認の writer、script finalisation、Git・Manifest の条件は維持する。`idle` 全体をまとめて削除しない。
4. **Workspace と Run**：利用状態、archive／cleanup、execution-only owner、container の専用実行分岐を整理する。通常の実行中 Run／process の確認、Run 終了処理、Manifest 確定まで一緒に消さない。
5. **Runner**：`execution_resource_id` や ResourceHolder／ResourceOperation への参照だけを外して機能を残さず、現行 execution bridge と Runner クライアントを廃止する。
6. **指示・文書・配布**：通常エージェントへ資源管理を要求する注入、agent guide、MCP metadata、共通 Skill と参照文書、README・Wiki・開発／配布手順を整理する。資源登録を前提とする運用記述を残さない。
7. **名称で誤削除しない**：parallel context、共有ストレージ、ホスト資源観測、OAuth 等を別機能として追い、単なる resource／shared の名称一致で削除しない。
