## 結論・実装目的（v2）
**DB と Run/Goal 状態モデルは変更せず、Goal の中断がカンバン上で RunningDots に見える問題だけを最小修正する。** 既存の Workspace 行にある掌（Hand）アイコンへ、Goal の要対応状態を接続する。新しい文言・件数・副状態・表示領域は追加しない。

> **ユーザー合意**：カンバンでは Workspace が複数あれば Workspace ごとに複数行がある。同一 Workspace の複数 Session に Goal が並列稼働することは可能だが、通常運用では稀。この例外のために複数状態や補助件数を表示するのは過剰品質。**人間が当該 Workspace を開いて対応する必要があると掌アイコンで分かれば十分。**

## 背景・調査で確定した事実（v1 から継承）
- 発端は LOCAL-432：Run は `running`、Goal は `blocked`、非同期質問は `async_specification`。カンバンは通常の実行中に見えた。
- v1 の Codex 調査（main `9c6f5f7`）では、`AgentGoalState.status` と `Run.status` は独立してイベント・投影に永続化されている。DB に必要な状態は既にあり、欠落は Workspace Summary / 表示用集約にあることを確認。Run `running` と Goal `blocked` は正当な組合せ。
- 上流 Codex の公開 `ThreadGoal` / `ThreadGoalUpdatedNotification` 型にはブロック理由フィールドが存在しないことを確認済み（下記参考）。理由を質問の存在から推測しない。
- 既存のカンバン列同期は Run の開始・終端に基づく。Goal 停止で列を動かす必要はない。

## 採用仕様：カンバン／Workspace 表示
1. **既存の掌アイコンを再利用する。** Workspace の現在の非終端 Run のうち、(a) 承認待ち、(b) Run の入力待ち（`awaiting_input` 等の正規の待機状態）、(c) Goal の `paused` / `blocked` / `usageLimited` / `budgetLimited` がいずれか一つでも存在すれば、通常の RunningDots より掌を優先する。概念上の優先順位は **承認待ち > 入力待ち > Goal 停止 > 実行中**だが、カンバン上の (a)～(c) の表示は**同じ掌アイコン**だけでよい。
2. **それ以外は既存表示を維持する。** 正常な実行中は RunningDots、準備中・失敗・終了済みなどは現在の表示契約を保持する。`is_running`（非終端 Run/実行中スクリプトの有無）の意味は変えない。
3. **通常モードのノンブロッキング質問は挙手条件にしない。** `async_specification` の未回答質問が存在するという事実だけで掌にせず、Run が実際に `awaiting_input` となった、または Goal 自体が停止状態であるなど、正規状態を根拠とする。質問と `blocked` の因果関係を推定しない。
4. **複数 Session でも特別な UI は作らない。** 現在の非終端 Run ごとに状態を判定し、Workspace には優先順位で定まる掌または既存表示だけを返す。別 Session が同時に動いていても、副アイコン・件数・別行を追加しない。過去の終端 Run に保存された Goal から現在の停止を誤判定しない。投影状態が不明・劣化している場合は古い Goal で挙手を捏造しない。
5. **表示経路を揃える。** 既存の Workspace カード（通常／コンパクト）と、同じ状態を表示する既存サイドバーなどで正しく掌が選ばれるよう、重複した判定を必要最小限で共通化する。ただし新しい汎用状態管理レイヤーや新しい表示部品を設けない。

## 明示的な非対象
- **DB スキーマ・Run enum・Goal enum・Goal イベントの変更なし。** Workspace に単一の goal_status カラムを追加したり、状態を二重管理したりしない。
- **カンバン列は変更しない。** Goal 停止で Issue を In Review 等へ自動移動しない。
- **カードのレイアウトを変更しない。** 「ブロック中」等の文字、未回答件数、副状態、バッジ、ツールチップの新設は不要。既存の掌・RunningDots の使い分けだけを修正する。
- **Workspace 詳細の Goal「再開」ボタンは現状維持。** LOCAL-432 では、質問パネルの不具合があっても再開と通常メッセージにより作業継続できた。未回答質問を理由に再開を無効化したり、質問回答と再開の操作を統合したりしない。
- 質問送信・再送の障害は **LOCAL-434 の責務**。LOCAL-435 に実装を拡張しない。LOCAL-432 の実行状態への操作・変更もしない。
