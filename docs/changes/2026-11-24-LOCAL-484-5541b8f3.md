## 結論
同じ Issue ID の本文がすでに Git に保存されていても、新しい自動マージを止めない。保存が ON の場合、前回保存した同一 Issue の本文と比較し、同じなら追加せず、変わっていれば採用本文の全文を別の Markdown ファイルとしてコミットする。既存ファイルは上書き・削除しない。

> **人間の意図**：LVK の DB に閉じず、Git だけで各マージ時点の設計意図を辿れるようにする。Wiki は現在の知識、イシュー本文の控えは過去の意図を担う。LOCAL-399 では初版の再マージを先送りした。

## 仕様
- 対象候補の Git ツリーにある既存の控えを、YAML フロントマターの `issue_id`（UUID）で照合する。本文中の ID や表示番号を同一性に使わない。比較対象は同じイシューの直近の控え。日付、タイトル、版 ID 等のメタデータだけが違っても本文が同じなら追加しない。いったん別本文になった後でさらに以前の本文へ戻った場合は、直近と異なるので新たに残す。
- 初回保存は引き続き可能。本文が変わった場合は同日であっても衝突しない別パスに書く。真正なパス衝突や Git コンフリクトを見逃さない。
- 同じ Integration の再試行では、最初に固定した採用版と保存計画を使い、後からの本文変更では再生成せず、二重コミットしない。保存を省略する場合も候補検証・コード取り込み・Wiki が従来どおり進む。保存 OFF 時の挙動は変えない。
- URL の公開用フィルタリング、過去ファイルの移行、ファイルエクスプローラ表示（LOCAL-483）、ワークスペースの復元・削除は今回の対象外。比較は現行の保存対象本文で行う。実装で既存の検証を緩めない。

## 確認条件
隔離したテストリポジトリで、初回→同じ本文で再マージ→更新本文で同日再マージ、過去本文への復帰、別 Issue ID、同じ Integration の再試行、保存 OFF、既存控え・検証と Wiki 進行への影響を確認する。実データや共有 dev を変更せず、main マージ・デプロイは行わない。日本語で結果と未確認範囲を報告する。
