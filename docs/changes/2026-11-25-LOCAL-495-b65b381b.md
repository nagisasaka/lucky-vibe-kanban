## 2. 実装範囲

- RustのMSRVを満たし、既存のnightly依存やchecksum-freshness等の運用に対応する固定toolchainを選択・検証する。調査で示されたnightly-2026-03-06は候補であり未ビルドなので、その版を無条件に必須としない。
- rust-toolchain.toml、DockerfileのRustベース、CI・共通setup action、sqlx-cli、devビルド／バンドル工程等の実際に利用する固定版を棚卸しし、整合させる。既存の対応プラットフォームを不用意に廃止しない。変更に必要なbindgen/libclang等の既存構成を維持。

### 2.2 SQLx 0.9 API追従

- 動的SQL：SqlSafeStrへの追従。動的識別子の生成元、allowlist、値のbindを確認した上で必要な箇所に公式AssertSqlSafe等を適用する。単なる機械的な無条件wrapでSQL injection防止の意図を損なわない。独自互換層は作らない。調査例：db/src/models/design_note_read.rs、repository_state.rs、server/src/remote_mcp/project_read.rs、server/src/routes/workflows.rs。
- Migration API：Migration::newのCow<str>→SqlStr等、migration_compat.rsの必要な型追従。既存のmigration SQLや履歴、LF/CRLFのchecksum互換、Project key migrationの互換分岐を維持。SQLiteの更新だけを理由に過去migrationを編集したり、新schema migrationを追加したりしない。
- Query macro/offline metadata：新版sqlx-cliに合わせて既存prepare-db / prepare-db:check等の導線を利用し、実schemaに対するmetadataを再生成・レビュー。型・NULL推論差分を確認し、手作業で不整合を隠さない。
- 型・hook：既存preupdate/update hook、lock_handle、SQLite value/refのSend/Sync制約等のAPI変更に対応する。callback内で必要なUUID/String等を取得している境界を確認し、現行の更新・削除通知を維持する。hookベース通知の再設計はLOCAL-497の責務とする。
- Transaction・pool・エラー処理：既存BEGIN IMMEDIATE、busy_timeout、DELETE journal、commit/rollback、BUSY/LOCKED分類と再試行、UNIQUE違反等の既存意味を維持する。RawSql、Arguments、transaction depthなど実際に影響するAPIを全workspace・all targetsで確認。SQLx更新を契機にDBアクセス設計を再構築しない。

### 2.3 既存データ・運用互換性

- SQLite更新のみを理由にDBスキーマ変更、VACUUM、データ変換、WALへの切替を行わない。現在のIssue、認証、Agent Runtime、実行履歴、Workspace、添付、各種設定等のデータ契約を維持する。

## 4. Goalの実行方式：メインによる自律的な構成選択

### A. 4方式の対等な選択

メインエージェントはGoal全体の責任を持ち、現行コード、変更間の結合度、担当成果の独立性、実装・調整・統合・検証の総コスト、利用可能な資源を考慮して、次の方式から最適な構成を自律的に選ぶ。

1. メイン自身による直接実装。
2. 同一Workspace内のネイティブsubagentによる調査・レビュー・実装分担。
3. ネイティブの担当subagent自身がstdio MCPで子Issueを起票し、別Workspaceのcoding agentへ委任する方式。
4. 上記の組み合わせ。

**4つは対等な選択肢である。** 子Issueの作成、fan-out、別Workspaceの使用自体は達成目標でも評価指標でもない。担当数、分割方法、fan-out数、子Issue数は固定せず、最低件数も設けない。分割不要と判断してすべて直接実装することも正当な成功である。形式的に方式2を実践したと示すためだけに子Issueを作成・サブエージェントを起動しない。

495の変更はRust toolchain、Cargo.lock、SQLxの共通API、metadata等の結合度が高く、各Workspaceで同じ重いビルドを繰り返すコストもある。一つのWorkspaceで共通依存更新を行い、必要な範囲だけsubagentに分担する方式が効率的かもしれないが、これは上位AIの判断材料であって指定された実行方式ではない。メインがコードの実態から選択する。

### B. 子Issue方式を選んだ場合

- メインが共通契約、依存／ビルド設定等の編集担当、作業分割、集約先・順序を必要な範囲で合わせる。重複した依存更新や共有ファイルの同時編集を避ける。
- 担当subagent自身が、自己完結した担当仕様と受入条件を作り、stdio MCPの公開契約に従ってparent_issue_idに本Issueを指定し子Issueを作成する。適切な既存Issueがあれば重複作成しない。
- 担当subagent自身が最新revision、実行設定、repository/branchを確認し、別LVK Workspace・Sessionのcoding agentへ実装を委任する。追跡、質問対応、レビュー、差し戻し、修正・再検証、受入れまで担当する。子Issueの作成やRun受付だけで担当完了としない。同一成果への修正は既存Sessionを継続する。
- 担当をまたぐ契約変更や衝突はメインが調整。親Workspaceの作業ブランチ等、既存の適切な統合手順で成果を集約し、一体のコードを検証する。子成果が散在したままGoal達成としない。
- 親と子のモデル・推論深さは実際の契約と担当範囲に合わせる。ネイティブsubagentと別Workspaceのcoding agentを混同せず、後者が親の起動設定を自動継承すると仮定しない。具体値は開始時／メイン判断とし本文で固定しない。

LOCAL-460の自然文フィルター再設計を議論する中で、Issueの全文検索（複数キーワードAND/OR）とEmbeddingによる意味検索を独立した検索機能として整備する方向になった。既存SQLiteにFTS5およびベクトル検索を組み込むことを想定している。現行SQLiteが古いことを踏まえ、人間はSQLiteそのものを最新へ上げる価値があると判断した。sqlite-fts5-bigramを採用するかどうかとは独立した課題とする。

上位AIの事前調査（未再検証）では、現行devはSQLx 0.8.6 → libsqlite3-sys 0.30.1 → SQLite 3.46.0をRustサーバーに静的リンクしており、FTS5が有効とされる。3.47.0以上を要求するsqlite-fts5-bigram等の拡張との互換性も議論の契機だが、特定のTokenizerやsqlite-vecの採用・実装は今回の範囲外。SQLx 0.9系ではlibsqlite3-sysの依存制約が緩和されたという先行情報もあるため、最新の公式情報と実際の依存解決で確認すること。

## 調査項目
1. 対象mainのSHAを明記。Cargo.toml / Cargo.lock / cargo tree等から、実際のSQLx、libsqlite3-sys、SQLiteのバージョン・リンク方式・feature・コンパイルオプションを確認する。可能であれば隔離された既存テスト等でsqlite_version()とcompile_optionsを確認する。コンテナのsqlite3 CLIの版と区別する。
2. 調査日時点のSQLite最新安定版、対応するlibsqlite3-sys・SQLx安定版、Rust/MSRVを一次資料で確認する。SQLx現行版を維持してSQLiteだけを更新する正規の方法があるか、SQLx 0.9系等への更新が必要・有利かを比較する。静的リンクの維持を前提とし、不要なfork、独自パッチ、動的リンク化、他依存の一斉更新は避ける。将来のSQLite更新を容易にする最小構成を推奨する。
3. SQLx更新を伴う場合の破壊的変更、全workspace crateのSQLx利用箇所、query macro/offline metadata、型・transaction・pool・migration・エラー処理、ロック・busy・WAL・BEGIN IMMEDIATE等への影響を具体的なファイルと根拠付きで棚卸しする。既存のSQLx以外のSQLite依存とのlinks競合やFFI ABI、重複リンクも確認。
4. 既存DBのファイル形式・schema・migration・PRAGMA・WAL/SHM・バックアップ／復元・Project export/importの互換性、既存インスタンスの安全な更新と旧版へのロールバック可否（更新後の機能使用による制約を含む）を調査。必要な検証計画を提示。
5. Docker/安定版・devのビルド/配布、既存Cargoキャッシュ、CI、プラットフォーム、ライセンス、既存テストへの影響を確認。FTS5が継続して有効になることと、将来的な拡張を利用できる条件を確認する（検索機能の実装はしない）。
6. 更新方法の比較、推奨する具体的な依存バージョン・変更対象、想定変更規模、リスク、受入条件・テスト計画をまとめる。推奨経路はKISSを優先し、余計な互換レイヤーを追加しない。バージョンや実行時検証など確認できなかったことは明示する。
