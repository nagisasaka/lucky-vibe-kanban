## 結論・目的

Git の移送と責務を分離した、LVK Project のエクスポート・インポート機能を設計する。開発版から安定版への Project 移行を具体例として、完了した記録と LVK が保持する固有データを別インスタンスへ持ち運べるようにする。本 Issue は仕様検討・対象棚卸しの起点であり、実装・データ移行・削除はまだ開始しない。

> 人間の意図：プロジェクトエクスポートは Git に関わることを対象外にする。移行前に未コミット変更をコミットし、必要なら push するという責務分担が KISS。DB だけでなく、アタッチメントや Change Manifest のローカル正本を失わず持ち運びたい。

## 合意済みの方針

1. **Git のデータ移送は対象外。** Repo 本体・Git 履歴・ブランチ・worktree の作業内容・未コミット差分を export に梱包しない。事前に未コミット変更をコミットし、移行先から必要な履歴を取得可能にするよう案内する。別ホストで取得する場合は必要に応じ push 等を利用者が行う。同じ Repo を再利用できる移行で push を一律必須にはしない。自動 commit／push／clone は行わない。
2. **LVK 管理下の場所は識別子・相対パスを正本にする。** 実行時に配置ルートから解決する。外部 Repo の配置など絶対パスに意味がある項目は import 時に移行先へ対応付ける。過去の会話・監査記録に文字列として含まれるパスを無差別置換しない。
3. **進行中処理の移送・途中再開は不要。** 進行中処理は移行対象から除外し、移行先では存在しなかったものとして扱ってよい。完了済み履歴と参照整合性は保つ。これは元インスタンスの処理をキャンセル・削除したり、未完了を成功扱いしたりする指示ではない。
4. **Change Manifest はローカル正本を対象にする。** Git 管理するオプションの有無で省略しない。
5. **Project export と全体バックアップを区別する。** export の処理を将来のバックアップに共用できても、Project の集合だけで認証・全体設定等まで復元できるとは扱わない。全体バックアップの検討は LOCAL-395。
6. 古いアーカイブ済み LOCAL-99 は本件の前提・再開対象にしない。今回の議論から整理する。
7. **エクスポートのDB部分は、対象Projectのデータだけを収めたSQLiteファイルとする。**

## 対象を確定するための棚卸し

対象 DB テーブル／JSON フィールドとファイルを、所有単位・参照元・再生成可否・export 採否で一覧化する。以下は必要対象と調査候補であり、ディレクトリ単位の丸ごとコピーを仕様としない。

- Project、Issue 本文・本文版・コメント・関連課題等の記録。
- 完了済み Workspace／Session／Run の履歴。DB 外の実行ログ JSONL や監査ファイルも調べ、移行後の履歴閲覧に必要な範囲を定める。実 worktree を持たない履歴と、新たな作業開始の扱いを分離する。
- **アタッチメントの実ファイルと関連付け。** 「cache」という保存先名だけで除外しない。各 worktree 内のコピーと中央の正本を区別する。
- **Project に属する Change Manifest のローカル正本と参照。**
- Repo 共通の persistent にある draft・公開用 snapshot・OpenWiki の中間物・復旧 checkpoint 等。成功後も残す価値のある記録と、処理中だけ必要な復旧情報・再生成可能物を分ける。
- Git 管理内の完成済み OpenWiki／ソースは Git 側で扱い、二重梱包しない。build cache、tmp、稼働プロセス、lock 等は持ち運ばない。

> 人間の意図：OpenWiki は生成に成功して成果物が残れば中間物は不要ではないか。persistent にあるから残すのではなく、残す本質的な価値を判定したい。Change Manifest はその価値がある。

この意図を踏まえ分類するが、既存中間物の削除や保存構造の全面変更は、この Issue の起票だけでは実行しない。

## 調査で見えている注意点

- worktree の `.lvk/shared/{persistent,cache,tmp}` は Repo 単位の外部領域を指す構成。同じ Repo を複数 Project が利用し得るため、shared/persistent 全体のコピーは他 Project の記録混入につながる。ID・参照に基づく選別が必要。
- `.lvk/attachments` のコピーと、cache 系の保存先に置かれる中央アタッチメント正本は別物。重要データを保存先名だけで判断しない。
- パス参照は DB の Repo／Workspace／Run だけでなく、request envelope 等の JSON、Manifest 関連ファイル、Wiki checkpoint にも入り得る。`storage_identity` のように名称が path でない項目も調べる。
- これらは調査時コードに基づく手掛かりであり、実装対象 revision で再確認し、網羅一覧とする。

## 追加調査：同一 Repo を複数 Project が利用する現状の安全性

**export/import の混入対策だけでなく、現在の通常運用そのものを独立して確認する。** 同じ Repo を複数 Project に登録した場合、Repo 共通領域の共有が意図どおりに成立し、Project 単位の処理が他 Project の記録や作業を壊さないかを調べる。

- 同じ実 Repo／Git common directory の登録時に Repo ID を再利用するか、別 ID になり得るか。共有領域のキー、パス正規化・symlink、storage identity と Project–Repo 関連の実態を確認する。同じ remote URL の別 clone は同じ物理 Repo と決めつけず、区別する。
- `shared/{persistent,cache,tmp}` の各データについて、Repo 共通であるべきものと Project／Workspace／Run に属するもの、その所有者識別・読み書き・列挙の範囲を整理する。
- 複数 Project での並列 Run、自動マージ、OpenWiki 生成・保守が、Manifest の選別・消費状態、draft／checkpoint、lock・一時領域を誤共有・上書き・競合させないかを確認する。共有が仕様である箇所は、その境界と影響を明示する。
- 一方の Project のアーカイブ・削除・Repo 関連解除・清掃が、他方で使用中の共有データや参照を消さないかを確認する。実データの削除・変更は行わず、コードと既存記録で調査する。
- 成果物では「現状の通常運用の問題」と「export/import 固有の課題」を分け、根拠・影響範囲・最小の対応案を示す。問題の存在は先に断定せず、この追記だけで修正実装を開始しない。

## 仕様化する論点

- export 単位と package 形式／schema version、対応 LVK バージョン、対象一覧・欠損検出。DB ファイルの丸ごと移送ではなく Project の参照閉包を明確にする。
- DB とファイルの一貫した取得時点。進行中処理を除外しながら、export 中の更新で完了履歴やアタッチメントの参照が壊れない取得方式。
- Repo の移行先登録・対応付け、共有 Repo の扱い。Git の物理移送はせず、利用者が用意した Repo を関連付ける。
- ID を維持／再採番する範囲、同一 Project の重複 import、既存 Issue／Repo との衝突。既存データを黙って上書きしない。別 Project への関連は欠損として検出し、方針を定める。
- ユーザー／担当者、executor/profile 等の全体設定への参照。秘密の認証情報を暗黙に梱包せず、再設定が必要な参照を可視化する。
- Session の履歴閲覧とプロバイダ固有セッションの継続可否を区別する。進行中 Run の復元は要求しない。
- 不正・欠損 package、import 中断時の失敗表示・後始末・再試行。パス traversal や意図しない外部 symlink 追跡を防止する。
- UI の入口、事前案内、含める／含めないデータと必要な Repo 準備の表示。全体バックアップと誤認させない。

これらは未確定の設計論点であり、追加の複雑な仕組みを初期仕様として確定したものではない。最小構成を提案し、レビューしてから実装に進む。

## 受入条件の方向性

- 別の配置ルートへ import し、**旧ルートを参照不能にした状態**でも Issue／完了履歴・アタッチメント・Change Manifest を参照できる。再起動後も確認する。同一ホストに旧ファイルが残るだけの試験では合格にしない。
- 複数 Repo・他 Project と共有する Repo でも、対象外 Project のデータが混入せず、内部参照が整合する。
- 進行中処理・キュー・lock を復活させず、Run が勝手に再開しない。除外範囲を説明できる。
- Git 本体／worktree 作業内容を含めず、export はソース Project と Git を変更しない。必要な未コミット／未移送の事前案内がある。
- 必要ファイルの欠損を黙って成功扱いしない。既存移行先データを無断で上書きしない。
- 対象・非対象一覧と最小仕様がレビュー可能になり、実装開始は別途指示を受ける。
