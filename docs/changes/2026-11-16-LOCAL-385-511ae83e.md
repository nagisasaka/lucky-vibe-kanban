## 実装スコープ（2026-11-17）
LOCAL-382の自動マージ検証後、LVKの登録Repositoryに対し、統合済みのローカルブランチ（mainに限らずdev等）を、明示操作で構成済みGitHub remote上の対応ブランチへ通常pushできるようにする。自動マージとは別の操作。新しいPR機能・自動push・force・任意URLの入力・既存Workspace×RepoのPR導線変更は対象外。

- Repo、設定済みremote、選択ブランチ、観測source SHA、宛先branchを操作前に明示し、権限・対象・SHAの再確認をサーバーで行う。認証は既存サービス経由で使い、トークンや秘密を表示・保存しない。
- GitHub認証拒否、保護ブランチ、non-fast-forward、source drift、結果不明を区別。正規の再確認手段を使い、勝手な再実行やforceへ切り替えない。既存UI/HTTPと必要なremote MCPの最小構成を選ぶ。push対象の履歴にIssueアーカイブが含まれ得るため、明示対象を確認できるようにし、自動公開しない。
- 隔離されたローカルfixture remote／mockだけで実装を検証する。実GitHubへのpush・設定変更・自動マージ・再起動はこの実装Runでは行わない。実装範囲、確認したSHA、検証結果を日本語で報告。

## 現在の目的・合意（2026-11-11）
LVKに登録済みのRepository用GitHub認証を使い、統合済みのローカルmainをLVKからGitHubへpushできる正規経路を整える。手動shellで認証を渡す回避策だけで完了にせず、Workspace branchのpushとRepository mainのpushを区別して扱う。

> ユーザーの問題意識：「でもさ、LVK から push できないのはちょっと厳しいよね。現状でも MCP 経由でワークスペースからは push できるのであれば、main から push できないのは片手落ちだ。」
>
> ユーザーの方針：「LOCAL-385 でこの問題に対処しよう。」

### 対象範囲
- 既存の認証ストアとGit serviceを再利用し、登録Repositoryの統合済みmainを通常のfast-forward pushで公開する操作を対象にする。
- remote MCPからも利用できるRepository単位の正規操作を目標とする。UI側は既存Repository管理・Git操作と整合する最小の導線を検討し、共通処理を使う。新しい公開管理画面、独立したGit実装、任意shell実行機能は増やさない。具体的なUI配置、stdio MCPへの公開方法・必要性は実装前に現行構成を確認して整理する。
- Workspace pushの既存機能を壊さず、mainをpushするためだけのWorkspace作成・branch付け替え・Workspace source準備を不要にする。
- tokenをshellへ取り出す、コマンドへ埋め込む、チャットへ渡す、汎用credential helperへコピーする手順を利用者へ要求しない。
- 受付前に対象Repository、remote、source SHA、destination branchが分かり、GitHub側の結果を確認できる。通常pushで拒否されたら止め、force pushや履歴書換えへ自動で切り替えない。

この段落の元の制限は要件更新時点のもの。今回は上記の限定された実装のみ開始し、実際のpushとdeployは引き続き対象外。

### 当初の申し送りと現在の扱い
> 当初の依頼：「その課題についてはイシュー化しておいて。ホスト側codexが対応できるかどうか分からないけど申し送りを作って」

当初の「ホスト側Codexだけで対応できるか」という調査観点は残すが、現在の目的はLVKから正規に公開できること。現時点で保存済みPATが無効とは判定できない。shell、LVKの認証ラッパー、Workspace用push、MCPの責務と権限を切り分け、KISSな最小構成で対応する。

## 固定SHAで確認した実装
確認元: `2e5a7fa7db4fc6e86388143ff8265066799e6d55`。以下は `query_repository` による固定commitの読取で確認。

1. `crates/git/src/cli.rs:889–921`
   - LVKのGit CLIラッパーはpush / fetch / ls-remoteのURL引数を解析する。
   - GitHub Repositoryに対応する保存済みcredentialを読み、`configure_git` で当該Git子プロセスへ設定する経路がある。
   - この仕組みが存在することと、任意のshell `git push` に同じ認証が供給されることは別。保存済み認証を利用しない経路の失敗を、保存済み認証の失敗と混同しない。

2. `crates/server/src/routes/workspaces/git.rs:169–214`
   - `push_workspace_branch` はWorkspace/Repositoryを特定し、Workspaceのsource準備処理を経て、`push_to_remote(&worktree_path, &workspace.branch, false)` を呼ぶ。
   - 対象はWorkspace自身のbranch。統合済みRepositoryのmainを指定する汎用入口ではない。
   - 別目的のWorkspace作成やbranchの付け替えでこの入口を流用する案は、必要性と副作用を確認せず採用しない。

3. `packages/web-core/src/shared/hooks/usePush.ts:15–30`
   - フロントエンドの`usePush`は`workspaceId`を受け取り、`workspacesApi.push(workspaceId, params)`を呼ぶ。既存UI側もWorkspaceを対象にした経路であり、この確認からmain用操作やMCP公開の存在を推論しない。

## 今後の実装の受入条件
- 登録済みのRepo用GitHub認証を内部利用して、LVKの正規操作から統合mainを通常pushできる。remote MCPの入口・必要な権限・UIとの責務が明確で、手動shellへのtoken転記を要しない。
- 必要な変更は既存の認証ストア・Git serviceを再利用した最小構成であり、tokenをIssue・ログ・応答・コマンド引数へ露出しない。
- 対象repo / remote / source SHA / destination branchと、未push・push完了・結果不明を利用者が判別できる。未確認のPAT無効を原因として表示しない。
- 許可範囲を超えるbranchやremoteの変更、force push、意図しないWorkspace生成・source準備処理を伴わない。
- 実装・検証を後日依頼された場合は、まず隔離テストで通常push、認証失敗、権限不足、branch保護、non-fast-forward、source drift、応答喪失時の扱いを確認する。実repoへのpush試験は別途その具体的な公開を許可された場合だけ行い、remoteの対象SHAで完了を検証する。
