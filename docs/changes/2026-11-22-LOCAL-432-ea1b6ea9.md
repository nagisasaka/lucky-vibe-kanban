## 結論・目的
正式リリース前の今、Lexical の旧版と複数の構文着色方式を温存するのではなく、**Lexical 0.53.0 への一括更新 + Shiki への全面統合 + Codex CLI に学ぶ会話表示の視覚的階層化**を、単一のリファクタリングとして行う。最終成果物を「美しく、速く、正しく、独自コードが少ない」状態にする。後方互換レイヤーや Prism / Shiki の並存設定は作らない。

> 合意済み：正式リリース前であり、統一のための合理的な退行リスクを許容する。段階的な恒久併存より、旧実装を積極的に整理・削除する KISS 方針を優先する。途中段階をリリース可能に保つ必要はないが、最終品質は確認する。

## 背景・既存実装
- LOCAL-340 の試着と LOCAL-421/422/423/424、LOCAL-425 で会話 UI や着色を改善したが、Codex CLI のような豊かな視覚表現にはまだ達していないというユーザー実感がある。
- LOCAL-425 Workspace の `e11f9de0` で確認した実装例：`packages/ui/src/lib/chat-code-highlighting.ts`（Prism 言語登録・フォールバック）、`components/CodeHighlightPlugin.tsx`（Lexical / PrismTokenizer）、`components/ChatCode.tsx`（シェル専用着色・here-doc 等）、`lib/code-highlight-theme.ts`（Prism token→CSS）、`packages/web-core/src/features/workspace-files/model/codeHighlightLines.ts`、`shared/components/MarkdownPreview.tsx`（rehype-highlight）、`app/styles/new/index.css`（意味色・strong）。Git diff は別の専用表示処理を持つ。
- `packages/ui`、`packages/web-core`、`packages/local-web` に Lexical 0.36.2 系の宣言がある。これは調査時点の実装例。Claude の再レビューでは `main` @ `9c6f5f7fea35217784b704d148416bf1e75f1cda` に主要な関連ファイルが存在することを確認済み。**着手時は対象ブランチ/HEAD と変更状態を再確認**し、このコミットや LOCAL-425 の内容が常に最新の main と一致するとは推定しない。
- Codex CLI は Markdown の構造に意味別スタイルを付け、構文色・差分色・テーマを分離している。端末用 ratatui/ANSI レンダラーの直移植ではなく、Web に適合する設計思想と配色体系を参照する。

## 実装要件
### 1. Lexical 最新化
- Lexical と利用中の `@lexical/*` を **0.53.0 に一括統一**する（着手時に最新安定版・互換性・ロックファイルを確認し、0.53.0 以外にすべき事情があれば報告）。一部だけ旧版に残さず、依存解決の重複を防ぐ。
- 0.36.2 以降の破壊的変更を追い、ESM、プラグイン、拡張、Node、Selection、Markdown 変換の必要な修正を行う。**エディタ構成および Shiki 統合は公式の Extension 方式を正本**とし、`LexicalComposer` から `LexicalExtensionComposer` への移行を対象とする。0.53.0 で非推奨（`@deprecated`）の使用箇所は原則として公式後継 API に置換し、旧 API 互換の独自ラッパーは増やさない。非推奨 API の置換は「新 API のためだけの全面書換えはしない」の例外だが、既存カスタム Node の `$config()` 化など、目的に対して著しく大きな変更を伴う場合は、現状・保守上の利得・規模を報告して判断を仰ぐ。**非推奨ではない API や正常動作する独自機能を、新しいという理由だけで一律に書き換えない。**
- 読み取り専用エージェント回答と編集可能な WYSIWYG の双方を対象にする。

### 2. Shiki に構文着色を統一
- **LVK が直接所有する構文ハイライト**は Shiki / TextMate ベースに一本化。Lexical 側は公式 `@lexical/code-shiki` / `CodeShikiExtension` 等、実際の 0.53.0 の安定・推奨 API を優先する（採否はコードで確認）。
- 会話の fenced code、コマンド表示、ツール呼び出し一覧と展開詳細、ファイルコード表示（`codeHighlightLines.ts` と `NormalizedConversation/FileContentView.tsx` の両経路）、Markdown プレビューを棚卸しして統一する。**言語指定のない inline code は Shiki による構文解析の対象外**とし、本文用の既存テーマスタイルで扱う。シェルのコマンド・フラグ・演算子・リダイレクト・here-doc 等も、適切な言語文法とテーマで読みやすくする。一般の引数/生出力を不正確に過剰着色しない。
- 独自 Prism 言語登録・トークン変換・複数実装・不要な `rehype-highlight` / `highlight.js` / Prism 依存と関連 CSS を削除する。実際に他用途が残るパッケージは機械的に削除しない。
- **Git diff の追加/削除・行番号・hunk・レビュー動作は既存専用コンポーネントを維持**し、構文着色は `git-diff-view` の**公式 Shiki 連携**を利用して差分表示には、`@git-diff-view/shiki` 0.1.8 の公式実装が固定している GitHub Light / Dark を **明示的な例外として許容**する。会話・通常コード・ファイル表示の Catppuccin Mocha / Latte は維持し、色一致のための依存パッケージへのパッチ・fork・独自アダプターは追加しない。diff エンジン自体は再実装しない。使用中の `@git-diff-view/*` のバージョンと公式連携の互換性を着手時に確認し、必要なら同系パッケージの更新を含める。
- 非対応言語、言語未指定、入力途中、長い/圧縮された入力、ハイライト例外は **原文を欠落させずプレーンテキストへ安全にフォールバック**。旧ハイライターへの互換フォールバックは作らない。

### 3. Codex CLI の視覚表現を参考に、Markdown 本文も改善
- Codex CLI の `codex-rs/tui/styles.md` と `markdown_render.rs` の思想を参照：本文、見出し階層、strong/emphasis、リンク、引用、リスト、インラインコード、コードブロック、補助情報、状態表示それぞれに意味ある視覚役割を与える。色数を増やすだけではなく、抑制・可読性・空間配置と一貫性を重視。
- Navy / Light の既存テーマを維持する。構文着色の第一候補は Catppuccin Mocha / Latte とし、Markdown 本文と Shiki の色設計を整合させる（詳細は「Shiki テーマ方針」参照）。
- Codex と Claude Code の両方の応答に共通して適用し、モデル出力に ANSI や色指定を強要しない。受信した内容の意味を表示層で表現する。

## Shiki テーマ方針（追加合意）
- **Navy は Catppuccin Mocha、Light は Catppuccin Latte を第一候補**とする。Shiki 標準テーマを優先し、独自テーマ・LVK 独自のトークナイザー・独自アダプターを増やさない。
- **Navy / Light の切替は Shiki 標準の複数テーマ出力を第一選択**とし、公式に対応する表示経路ではテーマ切替時の再ハイライトを行わない。**git-diff-view の公式 Shiki 連携だけは GitHub Light / Dark を使う**（ユーザー承認済みの例外）。公式 API が単一テーマ適用しか提供しないことを確認できた経路（Lexical、git-diff-view 等）では、テーマ切替時の再適用・再ハイライトを許容し、独自トークナイザー／アダプターによる回避はしない。
- Markdown 本文、状態表示、コードブロック背景などは LVK の既存テーマ体系で管理し、Codex CLI を参考にした意味別スタイルの改善もこの体系内で行う。既存の Prism 用配色定義は利用実態を確認して整理・削除する。
- 実表示で調和が取れない場合に限り、**① Shiki 標準の別テーマ → ② 最小限の CSS 上書き**の順で、追加コードの最も少ない方法を選ぶ。
- **実装上の確認事項：** Shiki 自体の複数テーマ出力は公式機能だが、Lexical 0.53.0 の `@lexical/code-shiki` / `loadCodeTheme` と `git-diff-view` の公式 Shiki 連携については GitHub Light / Dark 固定の公開 API を確認済み。各表示経路の実 API・バージョンを先に調査し、複数テーマ対応の経路では再解析なし、対応不可の公式経路ではテーマ再適用を選ぶ。後者は**既に許容された条件付き例外**として扱う。ちらつき・遅延・編集状態への影響は検証する。統一のために独自トークナイザーや恒久的な二重処理を追加しない。

## 非対象・KISS の境界
- Rust バックエンド、API、イベント保存形式、DB、エージェントの実行仕様を UI 着色のために変更しない。
- Lexical エディタ本体の作り直し、WYSIWYG の機能再設計、Git diff エンジン再実装、Codex CLI の Rust ターミナル描画コードの直接チェリーピックはしない。
- Prism/Shiki 切替設定、旧 API 互換ラッパー、独自抽象化フレームワーク、二重ハイライトエンジンを追加しない。
- 変更は広範でも、既存の実表示・編集・コピー・ツール詳細の利用契約は維持する。
