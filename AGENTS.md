# Repository Guidelines

## Project Structure & Module Organization

- `crates/`: Rust workspace; API and binaries in `server`, authentication in `server-access`, SQLx models/migrations in `db`, agent execution in `executors`, orchestration in `services` and `workflow`. See `Cargo.toml` for all members.
- `packages/local-web/`: React + TypeScript app entrypoint, shell and routes (Vite, Tailwind).
- `packages/web-core/`: Shared frontend features, pages and application services.
- `packages/ui/`: Reusable UI components and utilities.
- `shared/`: Generated TypeScript types (`types.ts`, `remote-types.ts`) and agent tool schemas (`schemas/`). Do not edit generated files directly.
- `assets/`, `dev_assets_seed/`, `dev_assets/`: Packaged and local development assets.
- `scripts/`: Development helpers; `deploy/`: server distribution and contributor tooling; `docs/`: documentation.

### Task-specific guides

- For documentation changes, read [`docs/AGENTS.md`](docs/AGENTS.md).
- For frontend changes in `packages/local-web`, `packages/web-core` or `packages/ui`, read the shared UI guidance in [`packages/local-web/AGENTS.md`](packages/local-web/AGENTS.md).
- Read `openwiki/quickstart.md` and relevant pages when present, and verify important claims against source, tests and configuration. Canonical `openwiki/` is read-only during normal development; only authorised maintenance updates it. The generated `.llm-wiki` Pipeline and knowledge-recall/enrich integration are retired: preserve existing files and do not initialise, update or run the legacy stages.

## Generated Types and SQLx Metadata

Edit the source Rust structs/enums and their `ts-rs` annotations, updating registrations in `crates/server/src/bin/generate_types.rs` when needed. Run `pnpm run generate-types` to regenerate outputs and `pnpm run generate-types:check` to check them.

Local board types retain the historical filename `shared/remote-types.ts`. They are generated by `crates/server/src/bin/board_types/` through the same commands; no Cloud backend is required.

For SQLx query or schema changes, use `pnpm run prepare-db` to regenerate query metadata and `pnpm run prepare-db:check` to check it. Both commands create a temporary SQLite database in this checkout, apply migrations, run `cargo sqlx prepare`, and clean up the temporary database. They require `sqlx-cli`; do not run them concurrently in the same checkout.

## Development Commands

Run commands from the repository root. Use the toolchain in `rust-toolchain.toml` and the pnpm version in `package.json`; package scripts and Cargo manifests define the actual command scope.

- Install dependencies when needed: `pnpm install --frozen-lockfile`.
- Run web + backend with automatically assigned ports: `pnpm run dev`.
- Backend watch with port setup: `pnpm run backend:dev`. Its watch command builds both `server` and `agent-process-host` before starting the server.
- Web development: `pnpm run local-web:dev`.
- Frontend type checks: `pnpm run local-web:check`, `pnpm run web-core:check`, `pnpm run ui:check`.
- Frontend lint: `pnpm run local-web:lint`, `pnpm run ui:lint`. `web-core` currently has no standalone lint script.
- Backend workspace checks: `pnpm run backend:check`, `pnpm run backend:lint`, `pnpm run backend:test`. All exclude `vibe-kanban-tauri`; lint includes all targets and `qa-mode`.
- Broad checks: `pnpm run check` runs the legacy path guard, frontend type checks and backend check. `pnpm run lint` runs local-web/UI ESLint, backend Clippy and the unused-i18n-key check.
- Broad formatting: `pnpm run format` runs `cargo fmt --all` and web-core/local-web Prettier. It does not include the UI package; use scoped formatting for normal changes.

### Rust build cache

- Use sccache for Cargo compilation when it is installed. Set
  `RUSTC_WRAPPER` to its absolute executable path, preserving any
  explicitly configured alternative wrapper.
- When `.lvk-shared/cache` exists, set `SCCACHE_DIR` to the canonical
  absolute path of `.lvk-shared/cache/sccache` before invoking sccache.
  If the shared directory is unavailable, keep the existing cache setup.
- Reuse the default sccache server (`127.0.0.1:4226`) and its automatic
  startup. Do not create workspace-specific server ports or sockets.
  Preserve an explicitly configured shared endpoint.
- An existing server retains its cache configuration. Check the actual
  cache location with `sccache --show-stats`; report a mismatch rather
  than stopping or reconfiguring a shared server.
- Keep Cargo target directories isolated per workspace. Do not place
  a common target directory in the shared cache.
- Preserve `CARGO_INCREMENTAL` and profile settings. Incrementally
  compiled crates are not cached by sccache; other eligible
  compilations can still benefit.
- Observe cache hits, misses and non-cacheable compilations with
  `sccache --show-stats` around relevant builds. Statistics are shared
  across clients; do not reset them or clear the shared cache.
- Do not set `SCCACHE_BASEDIRS` or change compiler flags routinely.
  Investigate path-related misses only when measurements justify it.
- If sccache is unavailable, use normal Cargo compilation and report
  that compiler caching was unavailable.

### Disk usage and temporary artifacts

- Reuse the workspace's normal build output directory across commands. Avoid
  creating a new target directory, checkout copy or dependency installation for
  every retry. When isolation is needed, track the temporary paths you create.
- Put disposable downloads, extracted archives, test databases, scratch builds
  and logs in a task-owned temporary directory. Arrange cleanup with a shell
  trap or language-level `finally`/temporary-directory helper, including on
  failure. Stop and wait for your test processes before removing their files.
- Before completing a task, remove your disposable intermediates that are no
  longer needed. Keep requested deliverables and enough evidence to explain
  failures; avoid retaining duplicate binaries, full build trees or repeated
  logs solely as evidence. Report any substantial task-created artifacts left
  behind, with their paths and the reason they must remain.
- Preserve the normal workspace `target/` and installed dependencies while they
  remain useful for ongoing work. Do not routinely run `cargo clean` or delete
  them after every check; remove obsolete task-owned scratch outputs instead.
- Before a large build, or when space is low, check free space with `df -h .`
  and measure specific known output paths with `du -sh -- <path>`. Scope
  inspection to your workspace and task-owned temporary paths; do not scan
  other workspaces or the shared cache as a whole.
- Before deleting an output directory, confirm its ownership, resolved path
  and that no process or retained result needs it. Git-ignored, old or under
  `/tmp` does not by itself mean disposable. Do not use blanket `/tmp` cleanup,
  `git clean -fdx` or `docker system prune` as routine task cleanup.
- `.lvk-shared/cache` is shared across workspaces and survives workspace
  deletion; `.lvk-shared/persistent` holds retained data. Do not clear either
  for local disk relief or put disposable scratch outputs in persistent
  storage. Shared-cache retention and capacity changes require coordinated
  maintenance, separate from ordinary task cleanup.
- Preserve LVK-managed worktrees, Integration/preview snapshots, instance
  builds, databases, backups and audit logs according to their lifecycle.
  In particular, retained staging source trees can supply frontend assets to
  running binaries. Leave managed cleanup to the owning workflow/operator;
  task completion or Card Done is not proof that these files are unused.
- If space remains insufficient after safe local cleanup, stop the expensive
  operation and report the measured usage and remaining candidates for owner
  review. Do not delete unrelated data to make a build pass.

## Validation and Completion

### Normal development

Choose validation for the changed behaviour and affected consumers. The broad commands above are available for cross-cutting changes; they are not a checklist for every task.

| Change | Validation to select |
| --- | --- |
| Documentation or instructions only | Check accuracy, paths, links and command names; review the diff and run `git diff --check`. No application build or test suite is needed. |
| Local Rust change | Target the affected crate with `cargo check -p <crate>`, `cargo clippy -p <crate> --all-targets -- -D warnings`, and relevant `cargo test -p <crate> <filter>` tests as appropriate. Include affected features and consuming crates for shared/API changes. |
| Web or UI | Run the affected package's type check, available lint and relevant existing tests; include consumers when shared components/types change. Frontend-only changes do not require Rust workspace checks. |
| Generated API types or SQL | Run the relevant generation/check commands above and tests for changed API behaviour, queries or migrations. |
| Routing, authentication or execution boundaries | Include regression tests across the affected boundary and relevant integration/E2E coverage. |
| Cross-cutting changes | Expand to affected packages and broad check/lint/test commands as needed. |
| Desktop | Run `pnpm run tauri:check`, `pnpm run tauri:lint`, and `pnpm run tauri:test` in a desktop-capable environment. |

- Add meaningful regression tests for new behaviour, bug fixes and edge cases, using existing test infrastructure. Text or formatting changes do not need new tests by default.
- Before running tests that include `production_fallback_keeps_api_misses_out_of_spa` (including the full `backend:test` suite), build the real frontend with `pnpm --dir packages/local-web run build` if it is missing or stale. The test requires `dist/index.html` and bundled JS/CSS; the build script's placeholder is insufficient. Tests in unrelated crates do not require this build.
- Run heavyweight Rust gates sequentially in a checkout. Server/container checks must exclude Tauri; unqualified `cargo check/clippy/test --workspace` includes it. Linux desktop validation needs GTK/WebKit development packages from the Tauri CI job; do not install them into the production image just for server checks.
- Format changed files or the affected package using its existing configuration. Avoid unrelated formatting changes and do not run the whole-repository formatter as a routine completion step.
- Review the final diff and run `git diff --check`. Report the selected validation, why it covers the change, results, and anything skipped or unavailable. Missing prerequisites and skipped checks are not passes. Repeat or broaden expensive checks only after new changes, failures or unresolved concerns justify it.

### Formal Integration

By default, formal server/container Integration must validate the frozen candidate with `pnpm run check`, `pnpm run lint`, and `pnpm run backend:test`, plus relevant boundary tests. The frontend prerequisite above applies. Desktop changes additionally require the Tauri gates in a capable environment. This contract is separate from scoped development checks: missing prerequisites are failures; fix the plan/environment and create a new Integration instead of bypassing validation. The explicit run-level “Skip all integration validation (unverified)” option is the supported exception: new runs inherit the saved server preference unless the request explicitly overrides it; when selected at admission, do not run acceptance checks or prepare their plan, and record the integrated candidate as unverified. This choice does not waive clean-candidate/ancestry checks, conflict-resolution review, target consistency, cancellation or publication protections. It cannot be enabled retroactively through agent instructions.

## Release and Deployment

Use the relevant guidance when working on distribution, deployment or isolated instance testing; publishing and deploying are task-specific activities.

- LVK is distributed only as Docker images. Do not publish npm packages or require npm authentication for validation. Historical npm instructions in legacy documentation or a local-only `PROJECT.md` are superseded by this policy.
- `.github/workflows/publish-server.yml` builds and validates the root Dockerfile's `server` target, then publishes version-tagged images to GHCR. Manual dispatch builds/tests without publishing.
- Do not run local Docker release builds unless explicitly requested. Source development/debug builds are supported locally or in the server development container.
- For server distribution changes, `pnpm run server:check` provides Docker-free kit tests alongside relevant source checks. Report skipped native tests and unavailable image/host validation. When deploying, verify the published image and use its immutable digest.
- For isolated instance testing or staging/deployment work, follow [`deploy/developer/STAGING.md`](deploy/developer/STAGING.md). Staging is opt-in contributor tooling, not a completion step for every task. Instance state must be separate from stable state via `LVK_INSTANCE_DIR`; debug/release is not an isolation boundary. Claim registered shared staging resources through resource coordination and stop test processes before releasing claims. Publishing an image does not deploy it.

### Shared development instance

- Build and run the necessary code, E2E and migration-compatibility checks in an
  isolated Workspace/instance. The shared public development instance is fixed at
  `/var/tmp/lvk-instances/dev`; do not use its data or running artifacts for tests.
- Before placement, identify the tested server, agent-process-host and frontend
  by actual hashes/build metadata, not checkout HEAD alone. Retain their required
  source/runtime paths outside cleanup or explicitly coordinate their retention;
  never overwrite artifacts still in use.
- Agents own candidate selection, builds, tests, prior migration-compatibility
  validation and work coordination. `start.sh` owns the authorised cutover;
  the server owns startup migrations. Preserve the instance DB, authentication,
  encryption keys and required launch settings. Placement is not cutover approval.
- Use the existing [development switch procedure](deploy/developer/switch/README.md)
  for CLI inputs, dry-run, backup and durable operation results. Coordinate idle
  work before switching; a successful dry-run alone is not permission to stop dev.
- After failure, inspect that operation's stage, logs, backup and actual process
  state using the linked recovery guidance. Preserve failed data and evidence;
  do not assume an old binary can use a migrated DB or perform an automatic rollback.

## Coding Style & Security

- Rust: follow `rustfmt.toml`; snake_case modules, PascalCase types.
- TypeScript/React: follow package ESLint/Prettier configuration and nearby naming conventions. Reuse existing components and keep functions focused.
- Public deployments start locked. Follow [`docs/self-hosting/authentication.mdx`](docs/self-hosting/authentication.mdx) for `server setup-token` and HTTPS Basic/Auth0 setup. Legacy nginx Basic is an optional migration layer, not the backend authentication configuration.
- Mock IdP/JWKS and browser fixtures do not prove real Auth0 or ChatGPT interoperability. Report live account validation separately.
- Use `.env` for local overrides; never commit secrets. Development ports and assets are managed by `scripts/setup-dev-environment.js`; key variables include `FRONTEND_PORT`, `BACKEND_PORT` and `HOST`.
