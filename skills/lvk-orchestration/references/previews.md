# Previews

## Independent Workspace previews

- When the user wants to try unmerged web changes, offer a preview from the relevant existing Workspace. For interactive UI refinement, investigate and recommend fast feedback methods supported by the existing toolchain, such as its development server, HMR or incremental builds, rather than repeatedly rebuilding distribution artifacts. Preserve authentication, exposure boundaries, data isolation and process management; do not add new infrastructure solely to speed up previews. Distinguish how changes reach the preview from final build-artifact verification, which still requires the relevant build. Delegate source/configuration changes and launch preparation to LVK Codex in an appropriate Session of that Workspace under the existing execution workflow. Keep this framework-agnostic and lightweight; do not introduce a dedicated UI or database-management system.
- Use LVK's development-server management for long-lived preview servers, not a server left under a coding AgentRun. Backgrounding or `nohup` does not guarantee survival after LVK cleans up that run. Use the supported UI or an actually available MCP tool; do not assume a development-server MCP exists. Verify that the server remains available after the coding run ends and that LVK can stop it.
- Reuse the repository's Dev Server script, executed in each Workspace's repository directory, with Workspace-local port and data configuration. Keep the managed server in the foreground rather than detaching it. If the shared script needs changing, explain its effect on other Workspaces and obtain authorization unless already covered; do not replace unrelated configuration or stop unrelated servers. Check process lifecycle separately from external routing, TLS and authentication.
- Consult the deployed container's documented external-to-internal preview-port mappings and select a free slot; proposed/example mappings are not evidence of available ingress. On a bind race, retry another available slot, never terminate an unrelated occupant, and report when no slots are available. Missing ingress is a prerequisite to surface, not permission to change nginx, Compose, identity-provider settings, or firewalls.
- Isolate databases and other shared resources by default. If handling is unspecified and consequential, ask only for the needed decision; do not repeat settled confirmations. Prefer test fixtures or explicitly authorized, minimal selective copies. Never share or modify live data or external resources without explicit permission; copied runtime paths, credentials, and background jobs are not automatically isolated.
- Preserve API authentication and scope secrets to the preview's needs. Verify startup and return the externally usable URL with its Workspace/revision and data context; distinguish local health from verified external reachability, and clearly state any unverified access.
- A preview request does not authorize merging, deployment, or production changes; keep those actions separate and explicitly authorized.
